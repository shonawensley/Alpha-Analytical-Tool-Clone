1. What the new docs are actually telling us
Tables: current failure mode

TABLE_RESEARCH and TABLE_INSIGHTS agree on the root problem:

Tables are “build once, reuse everywhere.” If you swap the workbook but don’t rerun the pipeline and/or clear caches, the tools will happily read stale _combined.csv files.

The legacy “in-page” mini-pipeline was removed; there is now one canonical pipeline (pipeline_runner) plus caching (@st.cache_data) in the app.

Both docs propose the same kind of fix:

Either purge existing *_combined.csv before generating tables for a new workbook, or

Use a run_id + separate output directory per run to avoid cross-run contamination.

They also recommend a small metadata/manifest file next to the tables that records: workbook filename, mtime, pipeline run timestamp, maybe a quick hash.

So: the docs don’t contradict anything—your plan (“fix tables first, then JSON, then Hot Zones”) is exactly what they suggest.

JSON mirror: what it should look like

TABLE_RESEARCH + JSON_HOTZONES say:

We do not need any legacy “string-table on disk” format; the CSVs under data/outputs/tables/<STATE>/ are the single source of truth. JSON is just a mirror.

JSON shape:

{
  "state_name": "OntarioCanada4",
  "sections": {
    "Midday": {
      "sets": {
        "Set1": {
          "draws": {
            "Draw1": {
              "draw_data": [...],
              "pattern_variations": {
                "R2": [...],
                "R4": [...],
                "R6": [...],
                "R8": [...]
              },
              "metadata": {
                "is_hot_zone": true,
                "hot_zone_count": 5
              }
            },
            ...


JSON is generated after the CSV/HTML tables pass manifest + schema checks (“build_json_tables_from_csv()”).

Minimal tests: for a known state/date, ensure Midday/Evening/Combined JSON match the CSV column counts, R2/R4/R6/R8 exist, and is_hot_zone lines up with star markers in the CSV.

Hot Zones: which design to trust

TABLE_RESEARCH + JSON_HOTZONES + HOT_ZONES all agree on the big picture:

Hot Zones is Module C, consuming JSON mirrors (and optionally Stable/DR/V-TRAC lean bundles), writing its own brain bundle under data/outputs/analysis/hot_zones/<STATE>/.

It should emit lean artifacts: per-item CSV, top-candidates CSV, meta JSON—matching the Digit Reduction / Stable “per_item/top/meta” pattern.

Your HOT_ZONES doc already contains a complete Part-2 engine (HotZonesEngine + CLI) that:

Reads a JSON table env (sections→sets→draws→R2/R4/R6/R8).

Mines late-column triads from starred boxes, tracking recency, vertical support, VT lanes, vt_only_lane, funnel_precol1, ls2_lane, etc.

Writes:

<STATE>_hotzones_per_item.csv

<STATE>_hotzones_top_candidates.csv

<STATE>_hotzones_meta.json (features list and config hash).

So the real problem is not lack of design—it’s choice and ordering: we need to pick one Hot Zones implementation and slot it after the JSON mirror.
