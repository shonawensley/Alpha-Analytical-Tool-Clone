Integration Plan: Installing 12 Profitability Trackers in AAT9 Control Center

Below is a comprehensive plan to implement each of the 12 “can’t-miss” profitability trackers (alerts A01–A12) into the AAT9 Control Center (Brain‑2). Each tracker section details its purpose, triggering logic (for both prediction and validation stages), the source data/fields needed from the existing sharepack environment, the expected output or UI log format, and any implementation notes (assumptions, potential blockers, and workarounds). This plan aligns with the final validation workflow and ensures each alert is a deterministic, testable rule that can be logged and tracked for profit contribution.

A01 – Dual‑Tail Consensus Break

Description & Goal: Alert A01 signals a high-conviction box play when the stable pattern extractor finds a dual-tail consensus (two elimination columns share the same last digit) combined with a strong 3-value pattern. The goal is to capitalize on scenarios where two tail digits consistently appeared (consensus) in recent elimination rounds, expecting the next draw’s winning combo to “break” that pattern by including those consensus digits. This yields a very small box set (often < 8 lines) focused on those tail digits, historically hitting within only a few draws.

Trigger Conditions & Logic:

Pre-Result (Prediction): If the Stable Pattern module’s output for a state indicates a consensus tail across at least two elimination rows (e.g. cons_tail_2d flag on R2/R4) and the top stable canonical pattern includes that tail digit, then A01 fires. In practice, this means checking the stable JSON for a high consensus_count (e.g. 2) or a boolean like cons_tail_2d=True on the state’s Combined run. Ensure the pattern is a 3-value (all distinct digits) pattern, as the Profit Blueprint emphasizes combining consensus tails with a 3-unique-digit pattern for faster hits. If these conditions hold (consensus tail present and pattern is 3-value), proceed to trigger. Optionally, require a basic Blackapple “foundation” (e.g. BA Status not Off) to gate false positives – i.e. only fire if the state’s BA score indicates some baseline alignment (≥WATCH).

Post-Result (Validation): After results, verify if the winning number indeed contained the consensus tail digits. The “break” means the prior consensus was resolved by the win: e.g. if tail “7” was consensual, check if the winner had 7 (or both tail digits if dual). Log whether A01 correctly anticipated the win. Also check decay: if no win, the alert “decays” after N draws (e.g. stop highlighting after ~5 draws if no hit) as suggested by median hit analysis.

Source Data & Extraction:

Stable Patterns JSON/CSV – Use the stable extractor’s output (e.g. *_stable_patterns.json or scores CSV) to get consensus flags and pattern details. Key fields: cons_tail_1d / cons_tail_2d (consensus tail in 1 or 2 columns), canonical (pattern string), perm (permutation count), rowcov (row coverage), and possibly consensus_count. The stable output likely already tags these (if not, ensure cons_tail_2d is computed by comparing tail digits of elimination rows). Also retrieve any stable indicator of 3-value pattern (could infer from perm or canonical length).

Blackapple (Aux) Data – For “foundation” gating, use BA’s status/triggers. From the Control Center’s BA table, retrieve the BA Score/Status for the state (e.g. is BA in ALERT or WATCH). Optionally check if BA triggers include the consensus tail (e.g. BA’s example combos – but simply using BA status as a boolean flag ba_foundation_ok is sufficient).

(No external table needed beyond stable and BA; VTRAC/HotZones not directly used in A01 logic.)

Output & Logging:

Alert Flag: In the state’s Control Center row, display an alert “A01 – DualTail Consensus” when triggered. The UI can list the alert code and a brief detail string. For example: “A01 (consensus tail 7, pattern 397, BA✔)”* indicating the consensus tail digit (7* means tail 7 repeating), an example pattern (397) containing it, and a BA checkmark if foundation is OK. Codex should compose this from evidence: the consensus tail digit(s), one top pattern (canonical) that uses them, and BA status.

Data Logging: Also log a structured entry in an “alerts” JSON or the state’s result JSON. Include alert_id: "A01", trigger_state: true/false, and an evidence object with keys like cons_tail_digit, rowcov, ba_foundation_ok etc. (as suggested by the design). This evidence_json is used for post-run analysis and to feed the explanation UI. For example: "A01":{"fired":true, "cons_tail":"7", "rowcov_3v":2, "ba_foundation_ok":true}.

Recommendation: Log the recommended play as well – typically Box play on the small set of combinations containing the consensus tail. The plan from docs suggests capping at ~12 lines for A01, so include play_type: "BOX" and list of combos or count. If the consensus pattern’s permutation count is 1 (only one combo fits), you might note an option to elevate to a straight play (e.g. "str8_elevation": true).

Notes & Implementation Hints:

Strength Metric: If available, capture a strength value (perhaps the stable consensus score or how many rows had the tail) to allow ranking multiple A01 instances. This could be stored as strength and used to sort “DualTail” alerts if multiple states fire A01.

Known Issues: Ensure the stable output actually provides the consensus flags. If not, Codex should add a small calculation in stable module: check tail digits of R2/R4 (and R6/R8 if applicable) – if two or more share the same digit, set cons_tail_2d=True. Also verify that the state’s table isn’t in a corner case (e.g. fewer than 4 elimination rows) – the spec notes that if there are too few rows, A01 should not fire erroneously.

Decays: Implement a simple decay mechanism: e.g. maintain an alert state with a counter for how many draws since fired; drop the alert after N draws if no win, per blueprint suggestion (median gap analysis).

Testing: Back-test A01 logic with historical data to ensure it triggers only when intended and hits frequently within the given window. Use Master Validation to confirm that when cons_tail_2d was true in stable, the alert would have led to a win within ~5 draws on average.

A02 – Doubles Accelerator

Description & Goal: Alert A02 highlights a scenario of a doubles bias – when the system predicts an imminent double-digit combination win under very low coverage. The goal is to accelerate betting on doubles (two identical digits) when multiple independent cues point to it: a pattern of overdue doubles in that state, evidence of a specific doubles family in analysis, and a stable anchor digit bias. Historically, this alert yields around ~6 combos or fewer to cover (often a single double family), making it a cheap but potent play. It leverages both the Digit Reduction and Stable tool outputs to catch when a double is “in the chamber” for a hit.

Trigger Conditions & Logic:

Pre-Result: Fire A02 if all of the following are true for a state’s latest run: (1) The Digit Reduction module indicates a double is favored – e.g. the DR output has a flag for “double 3-value” (meaning its top candidate has two same digits) or a high weight on double combos. Specifically check the DR JSON for something like is_double_pattern=true or if the top-ranked patterns contain only 2 distinct digits. Also check if DR shows a family bias (e.g. multiple top candidates share the same pair of digits – indicating a specific double family is emerging). (2) Due Doubles pressure: the state’s draws are primed for a double – for example, the top overdue double family is ranked in the top 3 overdue pairs (denoted by a “red” badge in the doubles summary). This can be determined via the Aux doubles panel in Control Center: if “Draws Since Double” is extremely high or a Top-3 overdue double pair is present, it signals the state is due for a double. (3) A Stable anchor supports this: check Stable Patterns output for any anchor digit or mirror that aligns with the double. For instance, if stable marked a particular digit as very persistent (perhaps a “single-tail consensus” on one elimination column, or an R-Consensus on a pair) that digit might be the double’s base. Additionally, if the last draw had a mirror pair (0/5,1/6 etc.) and our BA module flagged it, that could reinforce a doubles environment. In summary, A02 triggers when Digit Reduction + Stable + Aux all lean “double.” (The Profit Blueprint describes this as “single-tail with doubles bias” – one tail digit stands out and a doubles pattern is likely.)

Post-Result: If A02 fired, monitor upcoming draws for a win by a double combination, especially the predicted family. Log whether a winning combo with a double occurs and whether it matched the predicted family (true positive) or not (false alert). If a double hit, mark the alert as successful (and consider resetting any due-doubles counters). If no double occurs within a short window (e.g. 2–3 draws, since doubles can hit quickly when due), consider the alert expired.

Source Data & Extraction:

Digit Reduction Output – Analyze digitreduce_patterns.json or similar. Key fields: an indicator of a double pattern in top results. For example, some DR outputs label pattern types or provide counts of distinct digits per candidate. Codex can derive is_double_3v by checking if any predicted combo has exactly 2 unique digits (and length 3), and family_bias by seeing if multiple top combos share the same pair (like “11x” and “x11” both appear). If the DR module has a summary of pattern families, use that.

Aux Doubles Summary – Use the cross-state doubles table (Control Center’s “Draws Since Double” or similar). Identify if the state has an overdue double: e.g. a highlighted pair or a top ranking in that table. If the data is accessible via code, fetch the state’s longest-out double family and its “severity” (Red ≥1000 draws, etc.). Alternatively, use BA’s “pattern due” triggers: BA might tag “double out” if no double in N draws (this could appear in BA triggers text or we derive from draws history CSV).

Stable & BA Signals – From Stable, get any anchor digit flags: e.g. a cons_tail_1d (single tail consensus) which might suggest one digit likely repeats, or any mirror alignment (like a stable mirror flag). From BA, check the Mirror trigger of the latest draw if relevant, and BA’s overall status (should be at least WATCH to proceed). Also, stable’s output might contain a doubles-specific cue if any (not common, but stable might highlight doubles families in consensus bonuses). In practice, focus on stable’s top patterns: if one of them is a double (perm count=1 in a box context means a double/triple), that’s a strong sign.

Output & Logging:

Alert Display: Show “A02 – Doubles Bias” (or “Doubles Accelerator”) on the Control Center panel for the state. Provide context in the details, for example: “A02 (Double 33x bias, due-double 🔴, BA✔)”. Here 33x denotes the predicted family (e.g. “33” if expecting a double 3s), a red circle (🔴) or similar could signify the Top3 overdue double status, and BA✔ indicates BA foundation is positive. This string can be constructed from evidence: the double family or digit (from DR), an icon or text if the state’s due-double rank is top (from Aux), etc.

Logged Data: In the alerts JSON, record {"A02": {"fired": true, "double_family": "33", "due_double_rank": 1, "stable_anchor_digit": 3, "ba_foundation_ok": true}} for example. Evidence keys might include dr_double_flag (boolean), dr_family_digits, due_doubles_rank (e.g. 1 if most overdue, 3 if in top 3), and any stable consensus or anchor info (anchor_digit or mirror_echo_detected). The idea is to capture why the alert fired (e.g. DR predicted double, state had an overdue double, stable pointed to digit 3, etc.) for later review.

Play Recommendation: Typically Box these doubles. Since a specific double family is targeted, the coverage is small: one double family has 3 straight permutations (e.g. 33X yields combos 331, 313, 133) which as a boxed set is just 3 lines. Often we might cover two families at most (6 lines) if two candidates emerged. Log the intended combos if possible (e.g. under "A02": {... "suggested_plays": ["337","373","733"]} or shorthand family and count). If confidence is extremely high on an exact double, one could also list straight plays, but generally box is safer given doubles already pay double on box hit.

Notes & Implementation Hints:

BA Integration: If Blackapple provides a “Doubles” trigger or score, that can reinforce this alert. BA’s status “ALERT” often means multiple triggers, possibly including pattern due or floating digits – not directly doubles, but BA’s candidate list could contain doubles. We primarily rely on draws analysis for due-doubles.

Normalization of Terms: Ensure consistent naming for double-related flags. Digit Reduction might call a flag “double_candidate” while stable uses “perm=1” for a straight (which in a 3-value context could be a double or triple). Unify these into a clear boolean that Codex can check (e.g., implement a function to detect “isDoublePattern(pattern)” by counting digits).

Interim Approach for Overdue Doubles: If extracting the Top3 overdue double info from Aux programmatically is complex, an interim solution is to compute from the draws CSV: find the longest gap since any double appeared. However, since the Control Center already compiles this (and logs mention it was reinstated), Codex can likely call an existing helper (perhaps _rank_double_families used for CC doubles table). Mark this integration as done when that data is accessible; until then, consider A02 triggered only if DR/stable are extremely confident, to avoid missing the due-doubles context.

Testing: Use historical instances where a double hit after a long gap. Confirm that in those cases, DR had flagged a double and the alert logic would have fired. Tune the criteria if needed (for example, how “family bias” is detected in DR – maybe require DR’s top pattern is a double AND at least 2 of top 5 are doubles to confirm bias). Aim for A02 to fire only a handful of times but with a high hit rate (this was expected to be one of the most potent alerts).

A03 – Cross‑Variant Lock (Row Coverage)

Description & Goal: Alert A03 targets situations where a pattern is so stable that it spans multiple draw variants, essentially “locked in” across different drawings. The name refers to a cross-variant consensus – typically between Midday and Evening draws (or Combined vs individual variants) – that significantly narrows the candidate pool. The goal is to catch when the same pattern or digit set appears consistently in more than one variant’s analysis, indicating a very strong signal to play that pattern (often suggesting an automatic elevation to straight play if more than one permutation is possible). This alert usually yields a small set (~8 lines) or even fewer if one number overlaps variants.

Trigger Conditions & Logic:

Pre-Result: Fire A03 if there is evidence of multi-variant agreement in the stable patterns or elimination tables. Concretely, if a particular canonical pattern or tail is flagged in both the Combined run and at least one variant run (Midday or Evening) for the same state, it constitutes a cross-variant lock. AAT9’s stable extractor recently added multi-variant tagging, so each stable output row might carry tags like which variant(s) the pattern appears in. Use those if available: e.g. a pattern object might list "sections_found": ["Combined","Mid"]. If such a list length >1, that pattern is a cross-variant candidate. Another approach: run the stable analysis separately on the Midday and Evening draws (since Combined is the union) – if a top pattern (or any consensus flag) appears in both outputs, that’s a trigger. Additionally, consider Row Coverage: if a pattern has full row coverage (rowcov=4 in stable output, meaning it survived all R2/R4/R6/R8 elimination rows), that itself is a strong persistence signal that often correlates with cross-draw persistence. A03 can trigger on either condition: multi-variant presence or maximum row coverage. As a safeguard, require some BA foundation as well (e.g., state BA status ≥ WATCH) to ensure the state is active.

Post-Result: Validation involves checking if a predicted “lock” pattern actually hit. If the alert fired due to a specific pattern appearing across variants, see if that exact pattern (or one of its permutations) won in the next draw. Because this alert implies a strong pattern, often one permutation away from a straight, record if the hit was straight or box. If no immediate hit, apply a short decay – cross-variant consensus tends to indicate very imminent hits (often next draw or two). If cross-variant was an extended concept (like spanning multiple days), limit scope to avoid long lingering alerts.

Source Data & Extraction:

Stable Patterns (Combined & Variants) – Utilize stable analysis for each variant. The stable extractor output might already include variant info per pattern (especially if using the multi-variant mode). If not, run stable on Combined (all draws) and then on just Midday draws and Evening draws (these can be derived from the state’s draw CSV). Compare outputs: find any canonical pattern (3-digit string) that appears in more than one output. Also gather row coverage (rowcov) from the Combined stable output; flag any pattern with rowcov == 4 (or a high value like 3 if using fewer elimination rows) as a candidate, since full vertical consensus often indicates cross-draw carryover.

Hot Zones Overlap (if any) – The key inputs mention a “hot zone overlap helper” for A03. This could mean if a pattern is also highlighted by Hot Zones in one variant and stable in another. If Hot Zones module provides per-column star ratings, and the same digits appear in stable patterns, it strengthens the lock. Codex can thus also check hotzone output (e.g. hotzone_patterns.json) for any pattern matching the stable consensus.

BA Foundation – Check BA status (foundation) as usual. BA doesn’t directly provide cross-variant info, but ensure the state is generally “on” (this avoids chasing patterns in a cold state).

Output & Logging:

Alert Display: Show “A03 – Cross-Variant Consensus” on the CC alerts panel when triggered. Provide detail such as: “A03 (Mid+Eve lock on 47x, rowcov=4, BA✔)”. This indicates that pattern “47x” (some pattern with digits 4 and 7) was found in multiple variants (Midday and Evening, for example) and had full row coverage, with BA positive. The “Mid+Eve” can be inferred from which variants the pattern spanned. If rowcov was the trigger, mention it (rowcov=4 meaning pattern persisted across all elimination rows) as that is a similar concept to cross-variant persistence.

Logging: In the alerts JSON, an example entry: "A03": {"fired": true, "locked_pattern": "478", "variants": ["Mid","Eve"], "rowcov": 4, "ba_foundation_ok": true}. Include the pattern that was locked (or at least the canonical without a specific permutation if multiple perms), which variants it was seen in, and any other evidence (row coverage, etc.). If multiple patterns qualify, you might only log the strongest (perhaps highest stable score or smallest perm count). The evidence from stable output (like a persistence_set_count or similar field indicating it appeared in Set2→Set1) can also be logged if available.

Recommendation: If the locked pattern has more than one permutation (e.g. “47x” could be 4-7-? in some order), advise elevating to straight play or at least a half-box-half-straight strategy. The original guidance suggests auto-elevating to straight when cross-variant agreement is seen and perm > 1. So output could note: "action": "STRAIGHT (if >1 perm)" or simply indicate in the UI detail that straight consideration is on. Practically, list the small set of permutations to play (maybe 2 or 3 combos).

Notes & Implementation Hints:

Tool Coordination: This alert blurs module lines – stable primarily handles patterns per variant, while aggregator (Module E) was intended to unify cross-variant patterns. If the Aggregator is implemented by now, consider using it: the aggregator’s synergy report might list patterns and a field sections_found. If a pattern’s sections_found includes multiple sections (e.g. Combined & Midday), that directly signals A03. Using the aggregator output could simplify detection. If aggregator isn’t fully ready, the manual stable-run approach works.

Normalization: Ensure that stable outputs for different variants use the same canonical naming so they can be compared directly (they should, if using canonical patterns). The multi-variant stable analysis update likely already normalized this, but double-check that “All-Variant (C+M+E)” is labeled consistently if using any combined runs.

Partial Overlap: There may be cases where not the full 3-digit pattern but a pair of digits is common across variants (e.g. stable Midday highlights pattern 478, Evening highlights 479 – the “47” pair is common). Decide if this counts – the name “lock (Row Coverage)” suggests we want the exact pattern or a strong overlap. You might incorporate a simpler check: if two variants share two of three digits in a top pattern (a tail and an anchor digit maybe), it’s a quasi-consensus. However, to keep it strict, prefer exact canonical matches for now.

Hot Zones Caution: If using Hot Zones data to support this alert, note that Hot Zones might not be fully validated yet. As per the roadmap, treat Hot Zone-based factors carefully and mark them for later verification. It’s fine to include a HotZone overlap as a bonus (e.g. if a ★★/★★★ star column corresponds to the locked pattern, maybe bump the alert strength), but do not rely on it exclusively until confirmed.

Testing: Identify historical cases of cross-variant hits (e.g. the same number winning midday and then evening, or a pattern recurring across days). Ensure the logic would have flagged those. Also test a scenario of full rowcov=4 (consensus across elimination rows) – that should nearly always coincide with a hit or a strong near-miss. The Master Validation log suggests patterns with perm=1 or Set2→Set1 carry are exactly what A03/A04/A05 aim to catch. So A03’s detection should overlap with A01/A02 at times – ensure your implementation can handle co-occurrence (it’s okay if A01 and A03 fire together).

A04 – Order Dominance Carry‑Forward

Description & Goal: Alert A04 is about recognizing when one specific permutation of a pattern is dominating and continues to persist (“carry forward”) toward the next draw. In stable pattern terms, this often means a particular ordering of digits appears repeatedly at the top of elimination columns, suggesting a straight bias is forming. The goal is to catch these strong straight cues: for example, if one permutation (order) of a 3-digit pattern consistently outranks others through the elimination ladder, and that dominance carries into the final predictions, it’s a prime candidate for a straight play. This alert formalizes such situations, ensuring we log and consider them. It typically yields a single combo or just a couple, as it indicates a straight bet opportunity (or at most a very tight box).

Trigger Conditions & Logic:

Pre-Result: Fire A04 if the stable analysis shows order dominance of a pattern that persists to the end of the analysis window. Specifically, check for any pattern where perm > 1 (meaning multiple permutations exist for that canonical pattern) but one particular permutation is frequently present or highest-ranked in successive elimination rounds. The stable output may directly have an order_dominance metric or flags for “straight_lean” (some stable implementations tag a row if one permutation is repeated often). If not explicit, infer it: for a given canonical pattern, compare how many times each permutation of it appears in the stable elimination rows (R2, R4, etc.). If one perm appears in, say, 2+ rows while others appear rarely, that perm dominates. Another sign is a high score_straight or score_vtrac_straight in the stable scores (these fields indicate recognition of straight alignment). Also consider the “carry-forward” aspect: if the pattern or permutation was already present in the previous set (e.g., a Set2 → Set1 carry-over), that strengthens the case. Concretely, if stable JSON has something like persistence_set_count or similar, use it (i.e., pattern seen in prior set). So A04 triggers when one permutation of a pattern is highlighted strongly (straight bias) and either that pattern carried over from a prior context or remains top through the final elimination. A BA foundation check can be applied, but likely if a straight is forming, BA will often have at least one trigger (like mirror or root) on it – so BA check is less critical here, but still ensure the state isn’t totally cold.

Post-Result: If A04 fired, we expect an imminent straight or a near-miss. In validation, check if the winning number was exactly the predicted permutation (success) or if the canonical pattern hit but in a different order (partial success indicating maybe the straight lean was a false bias). If the target permutation did not hit within a few draws, drop the alert (the dominance was a false lead). Track stats: how often A04 leads to straight hits vs just box hits – this will inform if we treat A04 as a pure straight bet or just a very tight box scenario.

Source Data & Extraction:

Stable Patterns Scores/JSON – Use the detailed stable output (scores CSV or JSON) which likely includes columns for score_straight, score_perm, perm_count etc. For each canonical pattern, identify if perm_count > 1. If so, examine the elimination rows or the breakdown to see distribution of permutations. The stable spotlight or analysis log might help: it often notes if a canonical had one permutation in multiple rows. Codex could parse the stable JSON’s list of pattern instances (if provided) or use the CSV: e.g., if canonical=123 had entries like 123*, 312* in different rows, note counts. If one ordering appears in e.g. two rows and others only once, dominance = that ordering. Also, check stable’s carry-over: some output fields like set_chain or draw_chain length might indicate a pattern continued from previous set/draw. If set_chain >= 1 for a pattern, it means it was in the prior history segment – a strong persistence. Key inputs from design: stable’s order dominance flags and carry window data – ensure to extract those or compute them.

Winners Map (Previous draws) – Optionally, look at the last draw’s winner relative to the pattern: if the last winner was a permutation of the same pattern (just in different order), that’s a carry-forward scenario too (like pattern “123” won as “312” yesterday, and today “123” appears again – it could hit in order “123” now). This might be too advanced, but the concept of “break window” implies if a pattern almost hit (in wrong order or one draw off), it’s now due in the dominant order. If the data is accessible (e.g., through a winners JSON mapping patterns), use it to boost A04 signals.

BA/Aux – Not heavily needed here, but BA might have given a slight score to the dominant permutation if it aligns with a mirror or root. We don’t explicitly need BA fields beyond maybe confirmation that BA isn’t contradicting (foundation check as usual). Aux Positional might indirectly support if, say, it indicates one position strongly favors a certain digit coming first (positional heat). However, primary data is from stable.

Output & Logging:

Alert Display: Show “A04 – Order Carry-Forward” or “Order Dominance” on the CC panel. In details: “A04 (perm 528 dominating, Set2→1 carry, BA✔)”. This tells us pattern 258/285/528 etc. had 528 dominating in stable (that ordering appeared most), it carried from Set2 into Set1, and BA foundation is okay. We highlight the specific permutation “528” as the straight candidate. If no prior set carry, omit that part: e.g., “(perm 528 dominating, BA✔)”.

Log Data: Example JSON snippet: "A04": {"fired": true, "dom_perm": "528", "canonical": "258", "perm_count": 3, "dominance_count": 2, "carried_over": true}. Here dominance_count could be how many rows that perm appeared in, perm_count total permutations of the canonical, carried_over indicating if the pattern was seen earlier (or maybe a field if last draw had a related pattern). Include any straight bias scores from stable if available (e.g. score_straight for that pattern). All this evidence supports why that permutation was singled out.

Recommendation: Emphasize a Straight play on the dominant permutation. This is one of the few alerts where a straight bet is justified with minimal coverage (often 1 combo). If multiple permutations are close (say two orders are equally dominant), one might box those two – but usually A04 is about one clear winner. Indicate in output something like play_type: "STRAIGHT", combos: ["528"]. If not fully confident, one could suggest a small exact order wager alongside box (this can be left to operator judgment; our alert mainly flags the candidate).

Notes & Implementation Hints:

Precision of Detection: If stable’s algorithm already outputs something like a “straight lean” flag on a row, use it directly as A04. It likely sets that flag exactly when one perm is repeated across columns or has a high straight score. The stable master guide mentioned ensuring cons_tail and perm flags are correct and noted such features are central to alerts A01, A03, A04, A05. That implies stable output has much of what we need. Codex should hook into those fields (like straight=True or similar if present).

Carry Context: The term “through the break window” hints that even if the number didn’t hit in the immediate last draw, its dominance persisted. “Break window” could mean a draw or two where nothing hit, but the pattern remained. We should consider this implicitly handled by the pattern carrying from Set2 to Set1 (since Set1 represents latest draws segment). If more granular, one might track if the pattern was top in yesterday’s prediction but no hit occurred (like reading yesterday’s output from logs). However, integrating that might be beyond current scope – it borders on learning across days. Unless we have easy access to yesterday’s stable JSON, we can skip that and rely on intra-day evidence (Set2→Set1 in history covers a similar idea).

Potential Blockers: If the stable output doesn’t explicitly enumerate permutation frequency, Codex may need to compute it by parsing the elimination matrices (which might not be straightforward without modifying stable code). As a simpler proxy: if a canonical’s perm_count is 2 or 3, check if stable’s highest scoring row for that canonical has perm_index (or the actual perm digits) repeated in another row’s output string. Alternatively, stable’s score_straight > baseline could be used (if stable assigns extra points to patterns when one perm repeats, which is likely). Use whatever is most accessible.

Testing: Identify past scenarios where a stable pattern had one perm dominate. For example, a stable analysis log might note “canonical 167… no VT-straight credit even though index 17 is purely a straight lane” – that’s a case where a straight was hidden. Also “the 273 family represented as 237 all along the ladder” – here canonical 273 had order 237 appear consistently, which is exactly an A04 scenario. Ensure our logic would catch that (dominant perm 237). Test on known wins: if a number won straight, the prior analysis often had that permutation flagged. A04 should retroactively fire in those cases.

Overlap: A04 might often co-occur with A03 or A05 (they all deal with pattern permutation behavior). That’s fine – each alert logs a facet. E.g. a pattern could be cross-variant (A03) and also have a dominant order (A04) and even perm collapse (A05 if only one perm left). In implementation, ensure each flag is set independently if criteria met; the Control Center can highlight multiple alerts on one state (like “A03, A04” together) as needed.

A05 – Permutation Collapse

Description & Goal: Alert A05 identifies when the elimination process has narrowed a pattern down to essentially one remaining permutation, or a “collapsed” permutation space. This scenario occurs when, by the final stages of analysis, all but one ordering of a pattern have been eliminated – effectively indicating the system has zeroed in on a specific combination. The goal is to treat this as a must-watch straight scenario (or a trivial box of one) because historically once the permutation space collapses, a hit is imminent (or the analysis has found the exact number except ordering). A05 ensures we log these instances of near-certainty. It often overlaps with A04 but is an even more extreme condition (perm count = 1). Coverage here is the smallest possible (1 combo).

Trigger Conditions & Logic:

Pre-Result: Fire A05 if a pattern’s permutation count collapses to one in the analysis. Concretely, check stable output for any pattern where perm = 1 (meaning only one distinct permutation survived across all elimination rows). Many stable outputs explicitly provide perm for each pattern. If any have perm=1, that pattern is fully determined in order (all digits placed). However, we should apply some additional qualifiers to avoid trivial cases: e.g., if perm=1 happened very early or on a pattern with low support, it might be incidental. A12 – Triple‑Confirmed Carry Clamp

Description & Goal: Alert A12 is the ultimate convergence signal – it fires when a pattern or number is confirmed by three separate sources and has “carried” over time, effectively clamping down on a near-certain hit. This typically means a candidate that has shown up in multiple modules (Stable, Digit, VTRAC) and persisted through multiple draw sets (carried from deeper history into recent without hitting). It’s the “can’t miss” scenario where all lights are green: consensus across tools and time. The goal of A12 is to ensure we log and act on these extremely high-conviction setups with very tight coverage (often just a few straights or a single box). It’s called a “carry clamp” because the pattern has carried over (not hit) and now we clamp onto it for a final push, usually with a spend cap (since it might have been played multiple times already during carryover). Essentially, A12 is the system screaming “this specific number has been flagged everywhere and STILL hasn’t hit – it’s about to.”

Trigger Conditions & Logic:

Pre-Result: Fire A12 if a candidate pattern/number meets all of the following: (1) It has been confirmed by at least three independent indicators (e.g., appeared in Stable’s top patterns, in Digit Reduction finalists, and maybe also flagged by BA or VTRAC). In practice, this could be checked by seeing if the same canonical number or combination is present in the outputs of three modules. For instance, if stable_patterns.json, digitreduce_patterns.json, and aggregator or BA all mention “456” as a top pick, that’s triple confirmation. (Alternatively, stable+digit+VTRAC each found that pattern, which aggregator would note in modules_found). (2) It is a carryover pattern – meaning it was present in prior historical sets or previous day variant and still didn’t hit. This could be determined by stable’s persistence fields: e.g., if stable pattern entry has set_chain > 0 (it appeared in Set2 or Set3 and continued to Set1). Or by memory: if yesterday’s output also had this pattern and it remains today (the system might not easily have yesterday’s data unless we saved it or via master validation runs). But within a single run, stable’s set analysis covers some history: if a pattern is in Set3->Set2->Set1 chain, that indicates carry through history segments. So we can use stable’s persistence measures – if a stable pattern has persistence_set_count = 2 (meaning it was present 2 sets back) or something, that’s a strong carry. Also digit reduction might implicitly carry if it survived multiple days, but that’s harder to track; stable is our main clue. The conversation specifically hints “Set2→Set1 carry, as these are central to alerts A01, A03, A04, A05”, and A12 likely extends that to requiring multi-set presence plus multi-module. (3) It remains not hit yet (by definition since we’re predicting it now). So if the above criteria are true, A12 triggers. Another simpler path: if the aggregator synergy has a pattern with modules_found count >=3 (meaning found by 3 tools) and possibly a high sections_found or sets persistence, that could directly signal A12. If aggregator final_synergy.json is present, look for any entry with e.g. modules_found ≥3 and maybe an extra flag (some config might tag “carry” if not hit recently). If found, that’s A12. Essentially A12 is likely something the aggregator was going to highlight as top rank anyway; the alert just logs it explicitly with context.

Post-Result: If A12 fired, either we hit (great, likely a straight with nice payout) or we didn’t – if not, that’s surprising because triple-confirmed carries are expected to hit very soon. If it fails, either our signals were wrong or extremely unlucky. Possibly we’d stop playing it after some budget (the “spend-capped” note suggests maybe we only chase it a few draws). In validation, track A12 episodes: how many draws did it take to hit when A12 was on? Use that to set maybe a decay or budget (they mentioned an “episode with capped budget” future plan). For integration, just log it and assume we’ll handle stopping manually if needed (or incorporate a decay maybe similar to A01 but likely shorter – if triple confirm doesn’t hit in, say, 3 draws, something’s off).
