AAT9 Auxiliary Feature Integration – Comprehensive Plan
Part 1: Foundational Architecture & Scoring Logic Design

Principle – “Strings Lead, Aux Compounds”: The core design principle is that auxiliary features (e.g. due sums, pair gaps, V‑TRAC index streaks, positional pressure) should enhance but never override the primary string-based scoring. In other words, patterns identified by the Stable Pattern Extractor, Digit Reduction tool, and V‑TRAC Analyzer form the baseline score, and aux signals only add bonuses or confirmations
GitHub
GitHub
. This keeps the system aligned with the proven long-string methodology while leveraging aux data for extra confidence. A low-evidence candidate from the string tools should not be elevated to a top pick purely by aux features – the aux module can only boost or refine rankings, not create winners from scratch
GitHub
.

Treat Each Aux Feature as an Independent Signal: Architecturally, each auxiliary metric is computed as a separate feature with a stable key name and a boolean or numeric value
GitHub
. Examples include: “pair_is_RED” (true if the candidate contains a pair overdue beyond the RED threshold), “sum_is_due” (true if the sum or root sum is flagged overdue by Blackapple rules), “vtrac_index_overdue” (true if the candidate’s V-TRAC index is in an overdue status), “pos_top3_pressure” (count of positions where the candidate’s digit is in the top-3 most due for that state’s positional tracker), and so on
GitHub
GitHub
. Each such feature represents a distinct analytical signal derived from draw history. By keeping them separate, we ensure transparency and modularity – each feature contributes its own evidence without entangling the logic of others.

Config-Driven Scoring Weights: To turn these features into a score, use a configurable weight for each feature rather than hard-coding contributions. A practical approach is to maintain a YAML or JSON configuration (or a centralized Python dict) that maps each feature name to a weight (point value). For example, pairs.red_nonrepeat: 2 and pairs.blue_nonrepeat: 1 might specify that a RED overdue non-repeating pair yields +2 points, a BLUE yields +1, etc. This configuration could reside in a file like aux_features.yml or a Python module (aux_config.py), making it easy to adjust weights without touching the core code
GitHub
GitHub
. Initially, the weights should be small and intuitive (e.g. reward RED more than BLUE, significant aux alerts ~ a few points)
GitHub
. Each day’s analysis would load these weights and apply them consistently.

Score Calculation Logic: With feature values and weights in hand, the system computes an auxiliary score for each candidate pattern. The scoring logic can iterate over the feature dictionary for a given candidate and sum up contributions: for boolean features, add the weight if true; for scalar features (e.g. a rank or count), multiply by the weight to scale it
GitHub
. This can be implemented in a dedicated function (e.g. AuxScoreCalculator.score_features(feature_dict)) for clarity. A code stub from the design documents illustrates this clearly: iterate through each feature, add w if a boolean is true or w * value if numeric, accumulating a total score and recording each contribution
GitHub
. The result is a transparent breakdown of how each aux feature affected the score. Crucially, this aux score is additive to the base string-tool score and cannot single-handedly promote a candidate that has zero base score – the weights are chosen to ensure aux signals act as modest bonuses.

Single-Source-of-Truth for Feature Params: To maintain consistency, define all thresholds and parameters centrally (SSOT). The window lengths for analysis (e.g. 183 draws vs 360 draws) and the overdue thresholds (e.g. pair RED ≥56 draws, BLUE ≥37 for non-repeats) should be declared once in a config (e.g. core/aux_constants.py). All aux computations reference these constants, and even UI captions display them for clarity. For instance, if PAIRS_WINDOW = 360 in SSOT, the pair analysis uses the last 360 draws and the UI label might say “Overdue Pairs (window=360): red ≥107 (repeat), ≥56 (non-repeat).” Centralizing these values prevents drift between modules and ensures that the auxiliary features are computed on a stable, agreed definition across the app. The control config (perhaps aux_config.py) would export these constants, and modules like the Aux feature extractor, positional tracker, and Control Center import them so everyone speaks the same language (e.g. what “overdue” means)
GitHub
.

Wiring into the AAT9 Framework: In the AAT9 integrated app, the aux feature scoring module will be a self-contained component that plugs into the existing run sequence. Likely, after the Stable Pattern, Digit Reduction, and V-TRAC modules generate candidate patterns and base scores, an AuxFeatureExtractor runs on each state’s recent draw data (CSV) to produce current auxiliary stats (overdue pairs lists, sums statuses, etc.). These stats can be cached per state (e.g. stored in per_state/<STATE>/aux.json) so they are available for scoring and UI without repeated computation
GitHub
GitHub
. The scoring logic then evaluates each candidate pattern against these aux stats. For example, if a candidate contains a pair that appears in the state’s “Top 5 overdue pairs” list, the feature aux.pair_top5 would be true and scored. This design cleanly separates feature extraction (gathering raw signals from draw history) from feature scoring (assigning points and combining with base score). Configuration files like control_center.json and aux.json can specify which features and weights are active. For instance, control_center.json might include global toggles or weight multipliers for certain features if we want to easily turn some signals on/off or adjust influence across all states.

Transparency and Traceability: By treating each aux metric as its own scored feature with a name, we ensure every point awarded is explainable. The system will log not only the final aux score but also the breakdown of contributions per feature (e.g. +2 from a due pair, +1 from a consensus position hit, etc.). This traceability is key for both debugging and future learning. Every feature is defined in one place and used uniformly, building trust that the aux module behaves predictably. In summary, Part 1 establishes that we will build a config-driven, modular scoring layer where each auxiliary indicator contributes an independent signal, all calibrated by central constants and weights. This lays the groundwork for compounding signals and integration, which we address next.

Part 2: Compound Feature Detection & Synergy Scoring

Identifying High-Value Combinations: Beyond individual features, the framework should detect when multiple aux features coincide on the same candidate – these compound signals often carry elevated predictive significance. For example, suppose a particular number’s pattern triggers three aux alerts at once: it has a very overdue pair, its sum falls into a special Blackapple “hot” category, and its V-TRAC index is flagged overdue and on a repeat streak. Any one of these signals alone is notable; together, they might indicate an exceptional alignment of factors. The scoring system should recognize such synergy. Specifically, we can define rules like: if Feature A AND Feature B are both true for a candidate, then provide an extra bonus (or flag) for the combination. These combinations need to be chosen based on domain insight – e.g. a due pair + due sum + consensus positional gap could be one compound scenario to watch for, or “RED” overdue pair coinciding with a V-TRAC repeat index might be another.

Synergy Configuration: We will capture compound signal rules in a structured config (likely alongside feature weights). A simple approach is a list of synergy definitions, each specifying a set of feature keys that must all be true and a bonus score to add. For instance, a YAML snippet could look like:

synergy_rules:
  - when: [aux.pair_is_red, aux.blackapple_sum_red]
    add: 3    # bonus points if a candidate has a RED overdue pair AND a RED Blackapple sum alert
  - when: [aux.pair_is_red, aux.pos_consensus_3way]
    add: 2    # if an overdue pair coincides with a 3-way positional consensus


During scoring, after summing individual features, the algorithm checks each rule: if all features in a rule’s “when” list are true for the candidate, it adds the specified add points
GitHub
. The provided code stub in the design documents demonstrates this logic: iterate through synergy configs and, for each, verify all listed features are present/true; then accumulate a bonus and record that the synergy was “tripped”
GitHub
. This mechanism allows easy addition or tuning of compound conditions without hard-coding them. Initially, we’ll keep synergy bonuses modest – the idea is to confirm and slightly boost aligned signals, not to overshadow the base scores
GitHub
. For example, a +2 or +3 bonus for a powerful combo is reasonable, whereas making it +10 could overweight the aux side. The goal is to let compound aux cues reinforce a candidate’s strength in the rankings.

Flagging vs. Boosting: In addition to (or instead of) adding numeric points, the system can flag notable combinations as qualitative alerts. For example, if a candidate triggers the “due pair + due sum + index overdue” trifecta, we might tag it as an “Aux Compound Alert” in logs or UI. The architecture supports both: a synergy rule can contribute to score and simultaneously be recorded as a named event (e.g. list it in a "tripped_synergies" array)
GitHub
. This is useful for two reasons. First, it provides explanations – an analyst can see a special marker next to a candidate indicating “multiple aux factors aligned here.” Second, it enables aggregate monitoring. We could have the Control Center scan for any state where certain synergies are active (e.g. “State X has a rare aux compound situation today”). By registering combinations explicitly, either via flags or boost, we ensure the system doesn’t miss the forest for the trees when lots of aux signals converge.

Examples of Compound Signals: Consider a few concrete patterns the module should catch:

Overdue Pair + Positional Double Pressure: If a candidate contains a number pair that hasn’t appeared in >100 draws (very late) and one of its digits is the top overdue digit in the same position across Midday/Evening (positional pressure), that could be flagged. Such a scenario means both a pair gap and a positional gap align – a potential sweet spot.

Blackapple Sum + V-TRAC Index Repeat: If a combination’s sum is flagged by the Blackapple system (say it’s in the “purple” or “red” tier of expected-vs-hit anomaly) and at the same time the V-TRAC index for that combo is on a multi-day repeat streak, we have a sum-based hint lining up with a V-TRAC pattern. A synergy rule can detect this and boost the candidate slightly or mark it.

Consensus Alignment: If a candidate’s every digit is participating in some consensus or cross-variant due situation (for instance, two of its three digits are each the most overdue in some position across variant draws), that multi-positional alignment might deserve a compound bonus beyond the individual aux.consensus_count features.

By designing these rules carefully, we capture expert “compound” insights that often precede a win. Importantly, all compound detections still obey the earlier rule: they augment but do not overturn the overall scoring. A synergy might add a few points or highlight a number, but if the base string analysis score was poor, the candidate still won’t rise to the top. This keeps predictions analytically grounded. As we gain experience, we can adjust synergy definitions – the winners log (discussed later) will tell us which combinations actually correlated with hits, guiding us to refine or add rules.

Maintaining Manageability: The architecture for compounding signals should remain data-driven and transparent. Representing compound logic in a config (YAML/JSON) means non-developers can review and suggest tweaks (e.g., add a new rule for a scenario they observe). Also, by logging each time a synergy rule fires, we can analyze frequency and effectiveness. If a certain combo rarely triggers or doesn’t improve accuracy, we can drop it; if another appears very predictive, we can consider raising its weight. This approach ensures the compound scoring layer remains flexible and evidence-based.

In summary, Part 2 details how we’ll formalize combinations of aux features that merit extra attention. Using a synergy config, the Aux scoring module will detect these conditions and either boost the candidate’s score or mark it for the UI (or both). This compounds the predictive power of individual features when they reinforce each other, aligning with the user’s request to handle feature compounding intelligently.

Part 3: Integration with Aggregator & Output Panels

Flow of Information – From Aux Module to Aggregator: Once the aux scoring is calculated for each candidate, this information must feed into the AAT9 Analysis/Aggregator (the “Brain 1” per-state analyst and “Brain 2” Control Center in the big-picture design
GitHub
). In practice, after the core tools produce a set of candidate patterns (each with a base score/evidence from Stable Patterns, Digit Reduction, V-TRAC, etc.), the aux module attaches its feature evaluations and score for those candidates. We envision each candidate’s data structure (perhaps a dict or object) gaining an "aux" field containing something like {score: X, contributions: {...}, synergies: [...]}. The aggregator can then combine the base score with the aux score to produce a final ranking. Because aux scores are relatively small bonuses, a candidate that already ranks high from string analysis might get a nudge upward if it also has strong aux support. Conversely, a candidate with strong aux signals but low base score will remain filtered out if it doesn’t meet minimum criteria – we may even enforce a rule that only candidates above a certain base threshold are considered “playable,” regardless of aux (this could be a gate in control_center.json or similar config)
GitHub
.

Wiring via Config and JSON Outputs: The integration points are configured in the app’s JSON schemas and control files:

The per_state/<STATE>/aux.json (or equivalent) will likely store the raw auxiliary analysis for that state’s draw history each day – e.g. top overdue pairs, current sums status, positional data, etc.
GitHub
. The AuxFeatureExtractor can write this out so it’s available for reference. Additionally, after scoring candidates, a summary of top aux-supported candidates might be included here or in a separate file. For instance, aux.json could contain a list of the state’s highest aux feature scores of the day (for dev/analysis purposes or the optional “Aux watchlist” panel)
GitHub

The control_center.json is the aggregate brain’s daily snapshot
GitHub

The Control Center will use these to direct attention. For instance, if State A has multiple high-value aux signals (maybe a couple of RED flags across different categories), the control center can flag State A as a hot opportunity, especially if its string-tool output was also promising
GitHub
.

The Analysis/Aggregator Module (which compiles the final predictions per state) will read the candidate list with their augmented scores and decide which combinations to present as top picks. It may sort by the combined score. It may also apply explicit gates – e.g., only present candidates that achieve a certain total score or pass a profitability threshold. (As noted in design, the system uses rule-based gating for now – like require a minimum score or certain evidence – to ensure only high-confidence plays, until ML can refine this
GitHub

Communicating “High-Scoring” Aux Conditions: It’s important that when aux features significantly influence a decision, the system communicates that to the user. In the final output panel for each state, where the recommended numbers or patterns are listed, we will display the aux contributions as part of the evidence. For each winning candidate (or top N candidates), there could be an evidence breakdown like: “Base Score 8 (Stable Pattern X, VTRAC Y…), Aux Score +3 (due pair, overdue index) = Total 11”. Concretely, the UI might show small icons or text tags for each triggered aux feature. For example, a candidate might have tags like [Pair RED] [Sum Purple] [Index Overdue] indicating which aux signals it hit. If a synergy rule was tripped (compound event), that could be indicated with a special marker (e.g. “🔥 Aux Compound”). The design already calls for showing “evidence columns” or highlights from aux in the UI
GitHub
, which aligns with this approach. By exposing this info, the tool’s user can see why a number is favored – e.g. “This number is a strong stable pattern AND its pair is extremely overdue and its sum is in a hot zone, etc.”

On the aggregator side (Control Center aggregate view), the output would summarize noteworthy aux-driven situations. This could be as simple as a table listing any state that has an active “Due Doubles Watch” or “Blackapple Alert” or “V-TRAC Repeat Streak” on the same day
GitHub
. For instance, the Control Center might have a row that says: “TX Midday: Blackapple sum alert (sum 14 overdue), Due double (55 draws)” – giving a quick glance of aux conditions across states. It might also list an “Aux Heat” score per state, which could be a composite indicating the count or strength of aux signals currently in play (the design mentioned an “aux heat” rank as a way to identify states that “deserve attention today”

Pre-Prediction vs Post-Prediction Usage: Notably, the aux scoring module will be used before final predictions are made (during the daily run) to influence which patterns are chosen. It essentially adds informational content to the decision process: e.g., if two patterns are tied from the string perspective, aux can break the tie in favor of the one with more supportive features. After the draw (post-result), the aux features also help explain winners (more on logging in Part 4). The communication is thus twofold:

To the algorithm (aggregator) – via data structures and scores that influence the selection/ranking of candidates.

To the user/operator (UI output) – via clear annotations and panels that surface the aux-derived insights.

In implementation, the Analysis aggregator module will likely call a function in the Aux module to get a score and evidence for each candidate just before finalizing output. This could be wired in the main control flow or via the control_center.json pipeline. Because the modules are integrated through config, adding the Aux scoring is mostly a matter of including it in the processing sequence (e.g. an entry in a config that lists all scoring components to apply). The modular design (each tool outputting JSON and reading necessary inputs) ensures that by the time we aggregate, we have all pieces: string-tool scores, aux feature evaluations, and control center thresholds.

Final Output Panels: Each state’s final output screen will incorporate the aux info in a user-friendly way. Likely, the state panel already shows the top candidates and some key metrics; we will extend it with aux columns or tooltips. For example, next to a candidate number, it might show an “Aux Score” or simply list the top few aux features that applied. If the aux contribution was minimal, it might show nothing special (indicating the pick was mostly string-driven). If a candidate was heavily reinforced by aux (say it got +5 from aux features), it would show multiple aux tags. This approach keeps the operator informed. Additionally, the Aux “Self-Contained Watchlist” mentioned in design is a panel that shows the top 10 candidates by aux score alone across all states
GitHub
. This is primarily a diagnostic/secondary output – it’s not used to place bets directly, but it allows the user to see if any number purely on aux merits looked interesting. We can implement this by simply sorting all candidates by aux score and listing the top few (with their state/variant). It’s a way to validate that our aux scoring is sensible and to potentially notice any “dark horse” that aux loves (though our rules say we don’t act on aux alone, it’s still valuable info).

To summarize Part 3: the aux scoring module is seamlessly integrated into the AAT9 workflow by feeding its scores and flags into both the decision logic and the user interface. The Analysis aggregator module will use aux scores to fine-tune rankings (without violating any guardrails), and the Control Center will monitor state-level aux indicators. The output to the user will transparently display aux contributions, ensuring the enhanced predictions remain explainable.

Part 4: Winners Logging & Learning from Historical Outcomes

Daily Winners Log with Features: A cornerstone of this design is that every day, the system logs the actual winning result alongside all the feature values that were present or absent for it. This winners log is essentially our dataset for validation and future machine learning. Concretely, for each state and draw (e.g. “CT Midday 2025-09-12”), after the winning numbers are known, the system creates a JSON record capturing: the winning combination, the relevant context (e.g. V-TRAC index of that combo), and all the feature flags that our tools had generated for that combo on that day
GitHub
GitHub
. Under an "aux" section, it would list things like the total aux feature score the combo had, the top contributing features, and even which synergy rules fired
GitHub
. For example, a logged entry might show that the winning number 913 had vtrac.is_top10_overdue = true (+5 points), pos.double_pressure = true (+5), aux.pair_due.red = true (+6), and a synergy of vtrac+pos that added another +4
GitHub
. These values match how the system scored that number. By logging this, we create a historical record: was our scoring catching the right signals for the winners? Are there patterns in the features that often precede a win?

The log files are structured for both human and machine use. They reside in a directory structure like winners/YYYY-MM-DD/STATE_Draw.json for each day
GitHub
, or possibly combined per day. The important thing is that each JSON contains a feature vector for the outcome. The features logged include both the string-tool features (from Stable Pattern, Reduction, etc.) and the aux features. This means each entry can serve as a labeled data point (winning combination = true outcome) with a slew of predictor variables (the features). Over time, as we accumulate these daily logs, we get a growing dataset for analysis.

Enabling Backward Validation: With this logging in place, we can do backward-looking analysis to validate our approach. For instance, we can filter the logs to see all cases where a particular synergy was true and see how often that coincided with a win. If “pair overdue + sum red” happened 50 times and yielded 5 wins, that’s a 10% hit rate – perhaps significant. If another feature rarely ever appears in winning combos, maybe it’s not as useful as thought. This helps refine the model. Additionally, because we log the raw values (not just the points), we can experiment offline with different weighting schemes or ML models to see if we’d have caught more winners with different tuning. The log essentially lets us replay history with new scoring ideas.

Learning and Tuning: The presence of complete feature logs paves the way for machine learning and systematic tuning:

Manual Weight Tuning: In the beginning, we expect to adjust the feature weights by inspecting the winners logs. For example, if the logs show that many winners had a certain feature true but our current weight for it is low, we might decide to increase that weight to boost candidates having that feature. The design explicitly suggests using the logged outcomes as an “evidence engine” to guide weekly weight updates
GitHub
. Because everything is logged, we can do this empirically rather than by gut feeling.

Machine Learning Model: As a next step, once we have enough logged data, we can train a simple ML model (e.g. a random forest or gradient boosting decision tree) using the features as inputs and the “win or not” as output
GitHub
. This model could learn optimal weightings or interactions among features. We’d compare its performance to our rule-based baseline. Importantly, any ML introduction will not replace the rules and guardrails we have – it would serve to refine the scoring within the safe bounds we set (the philosophy is to keep the human-understandable rules in front and use ML to fine-tune, not to drive the car blindly)
GitHub
GitHub
. In practice, this might mean ML suggests new weights or thresholds, which we then adopt in our config (keeping the system behavior interpretable).

Closing the Loop: Over time, the daily logging and periodic learning create a feedback loop. The tool “learns by doing” – each day it logs results, we adjust or train, and the next iteration of the scoring is a bit better. Because we never overwrite old logs (each run is saved with a unique ID and date)
GitHub
, we can always go back and verify that changes are actually improvements. If we change a weight configuration, we won’t delete the past data; we just start logging under a new run ID. This is valuable for A/B comparisons and regression testing.

Continuous Improvement and Monitoring: We will make it a practice to review the winners log regularly. If some aux feature never appears in winners or doesn’t contribute, we might drop it or lower its weight. This process is essentially the system learning from its own history.

In conclusion, Part 4 emphasizes that our approach is not static – it’s built to learn and adapt. Every auxiliary feature we integrate is logged and can be evaluated against real outcomes. The winners log serves as both a validation tool (did our features behave as expected?) and as a training dataset for future enhancements. By designing the logging from the start, we ensure that the AAT9 tool can evolve into a more intelligent system over time, leveraging data to tune its analysis while maintaining the clear, rules-driven foundation. Each piece of aux data we log today could be the key to smarter predictions tomorrow, and our architecture fully supports that evolution.
