Great question—and you’re thinking about it exactly the right way. Here’s the crisp clarification and what to do next.

Short answer

Excluding pure triples (000, 111, … 999) from the V‑TRAC reference is fine and not the cause of the Delaware issue.

277 is not a pure triple. It’s a double whose V‑class pattern is 333 (because 2→3 and 7→3 in your DIGIT→V map).
With the reference you pasted, get_vtrac_index("277") must return 26 (Index 26: VTRAC 333, Doubles [227, 277]).

If your Delaware run only surfaced family id 2 (for 010) and not 26 (for 277), the problem is almost certainly a lookup wiring or population gap, not your decision to omit pure triples.

Why this is true (one level deeper)

Your guard in get_vtrac_index that returns None for triples only fires when the raw digits are all identical (len(set("000"))==1).
It does not (and should not) fire for “class triples” like 277 where all digits map to the same V‑class.

In the rows table you shared, Index 26 (V‑TRAC 333) explicitly lists "Doubles": ["227","277"], so if that table is what your runtime loads, 277 → 26 is guaranteed.

What likely went wrong in Delaware

One of these is almost always the culprit:

Wrong module being imported
alpha_analytical/vtrac forwards to modules.vtrac_reference. If the app (or winner_family_spotlight.py) is actually importing an older copy (e.g., under scripts/auxiliary/working/modules/), it may be missing 277 in Index 26.

Lookup population missed 277
If the working reference rows omitted "277" in the doubles for 333, the in‑memory VTRAC_LOOKUP would never learn it—even though your canonical list should include it.

Over‑zealous normalization
A stray “dedupe digits” step before lookup could reduce "277" to "27" or "77". (Your current helper shouldn’t do this, but it’s worth checking.)

B) Add a safe fallback by class (prevents future table drift)

Inside get_vtrac_index(s) after trying the table lookup:

# 1) try explicit table (fast path)
idx = VTRAC_LOOKUP.get(s)
if idx is not None:
    return idx

# 2) bail only for *pure* triples of raw digits

    return None  # keep legacy behaviour for 000/111/...

# 3) fallback by class (makes 277 -> '333' -> 26 even if rows missed it)

idx = INDEX_BY_VTRAC.get(vcode)  # e.g., {'111':1,'112':2,...,'333':26,...}
return idx
