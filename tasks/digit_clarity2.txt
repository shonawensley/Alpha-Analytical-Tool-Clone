You’re on the right track. Let me answer your three questions directly first, then I’ll give you a concrete “do this next” list for Codex so we lock the lean shape for Digit‑Reduction and replicate it across the other tools.

1) Is *_digit_reduction_steps.csv part of the predictive “brain,” or just diagnostics?

Short answer: it’s diagnostics.
Why: the analyzer’s brain is the feature pipeline that consumes the reducer’s in‑memory reductions and emits the per‑item features and the top‑candidates. The steps.csv is a trace of how each R2 string was reduced step‑by‑step—great for debugging and validating, but not required for inference or scoring.

Think of it like this:

R2 strings  →  reducer (does the reductions)  →  analyzer_v2 features/score (the brain)
                │
                └── steps.csv (optional trace for humans / tuning)


So we should:

Keep *_analyzer_v2_per_item.csv, *_analyzer_v2_top_candidates.csv, *_analyzer_v2_meta.json (these are the predictive brain outputs).

Gate *_digit_reduction_steps.csv behind a diagnostics.write_steps_csv flag (off by default).

Drop the 30k‑line *_digit_reduction_log.json entirely unless explicitly requested. It duplicates information the code already “sees” and only adds noise/size.

2) Why keep any “winners” outputs once we have the 3‑variant pattern view?

You’re right that most per‑tool winners artifacts are post‑result forensics and should be centralized. But keeping a very small, central set helps with:

Human review: one overlay HTML that paints the winning pattern across the three tables (the view you like).

Machine audit/repro: a tiny stamp/meta JSON so we (and future runs) know which draws, configs, git SHA, and variants were stamped.

(Optional) coordinates: if you ever want automatic QA metrics or to compute hit rates without re‑parsing HTML, keep a compact map.json (grid coordinates + labels). This is machine‑readable and ~tiny.

Everything else (hits.csv, flags.csv, per‑tool overlays, etc.) is redundant once you centralize. So the central Winners Module should produce at most:

/winners_central/
  YYYYMMDD_overlay.html        (human)
  YYYYMMDD_stamp.json          (repro metadata)
  YYYYMMDD_map.json            (optional; machine coordinates for QA)


…and no analyzer should write its own winner_* files by default.

3) Why archive/guard extra clustering outputs instead of deleting them?

Three reasons:

Risk control: the clustering and detector code often feeds feature columns you do keep (e.g., density, earliest/persistence, drop/v‑trac detection). Hard‑deleting assets can break paths you’ll need when you revisit scoring.

Cheap compute, high reuse: these calculations are light and already happen inside the brain pipeline. What we’re cutting is surface area of files, not the internal computations that produce your useful columns.

Repro/debug: archiving (or gating behind diagnostics) lets you re‑enable traces quickly when you’re tuning against a new week of pick3statC4, without re‑adding code.

Net: turn off the writes, keep the internal features that matter, and park any heavy/debug artifacts behind diagnostics flags.
