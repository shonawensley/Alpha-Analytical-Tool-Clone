What those errors mean (and whether to worry)

1) stream error: 400 {"detail":"Unsupported model"}
These lines come from a helper trying to talk to an external LLM to auto‑edit docs. They’re not your app and they don’t affect rendering or tests. Safe to ignore.

2) PowerShell “ParserError / Unexpected token 'chip' / MissingEndParenthesis”
That’s just quoting. The script tried to splice HTML/CSS text into Python using double‑quotes inside double‑quotes. Nothing is wrong with your Python; the patch command itself is malformed. Use here‑strings or (better) edit the Python once directly rather than “replace in place” from PowerShell.

3) Cannot find path 'C:\Users\User\src\core\module_c_vtrac.py' and similar
These happen when commands run outside the repo root or when the file path is slightly different. Your canonical layout’s entry and pages live under src/app.py and src/core/…; always run from the repo root (that’s what run_app.bat does) to avoid path drift.

4) “The directory name is invalid (os error 267)”
Usually the same root cause as (3) or a $path variable that includes stray quotes/newlines.

Bottom line: nothing here corrupts your data. It’s just automation struggling with quoting and paths. Don’t “let it keep running” in this state—ship the overlay with a tiny, deterministic patch instead.

The minimal, safe way to ship the yellow overlay

The key is to treat “long‑string windows” as data and keep the V‑TRAC renderer ignorant of how they’re produced—only whether a given (Set, Draw, RowType, Column) is inside one of those windows.

1) A tiny descriptor module (if not already present)

File: alpha_analytical/digit_reduction/long_string_windows.py

# alpha_analytical/digit_reduction/long_string_windows.py
from __future__ import annotations
from dataclasses import dataclass
from typing import List, Tuple, Literal

TableKind = Literal["midday", "evening", "combined"]

@dataclass(frozen=True)
class LongStringBox:
    table: TableKind
    sets: Tuple[str, ...]
    draws: Tuple[str, ...]
    row_types: Tuple[str, ...]
    columns: Tuple[int, ...]     # numeric table columns to tint

# LS “windows” we want to keep visible during analysis.
_COMMON_WINDOWS: List[Tuple[Tuple[str, ...], Tuple[str, ...], Tuple[str, ...], Tuple[int, ...]]] = [
    (("Set3", "Set2", "Set1"), ("Draw1",), ("R2",), (7, 6, 5)),  # top band across 7/6/5
    (("Set1",),               ("Draw4",), ("R2",), (3,)),        # S1/D4 col 3
    (("Set1",),               ("Draw6",), ("R2",), (1,)),        # S1/D6 col 1
]

_VALID_TABLES: Tuple[TableKind, ...] = ("midday", "evening", "combined")

def get_long_string_boxes(table: str) -> List[LongStringBox]:
    key = str(table).lower()
    if key not in _VALID_TABLES:
        return []
    return [
        LongStringBox(table=key, sets=a, draws=b, row_types=c, columns=d)
        for (a, b, c, d) in _COMMON_WINDOWS
    ]


Why here? It keeps the “where to highlight” logic next to Digit‑Reduction and away from BA/Aux (which only read draws CSVs and do not touch string tables). That matches your architecture decisions.

from functools import lru_cache
from alpha_analytical.digit_reduction.long_string_windows import get_long_string_boxes

def _norm(x: str) -> str:
    return str(x or "").strip()

@lru_cache(None)
def _ls_coords(table_kind: str) -> set[tuple[str, str, str, int]]:
    coords: set[tuple[str, str, str, int]] = set()
    for box in get_long_string_boxes(table_kind):
        for s in box.sets:
            for d in box.draws:
                for r in box.row_types:
                    for c in box.columns:
                        coords.add((s, d, r, int(c)))
    return coords

def _is_ls_cell(table_kind: str, set_name: str, draw: str, row_type: str, col: int) -> bool:
    return (_norm(set_name), _norm(draw), _norm(row_type), int(col)) in _ls_coords(table_kind)
