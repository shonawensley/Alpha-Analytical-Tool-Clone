AAT9 — Big‑Picture Brief for Codex (Part 1)

Vision, guardrails, data contracts, scoring posture, and immediate build plan

North‑star. Use long‑string progression tables (R2/R4/R6/R8 over 7→1) to surface a small set of high‑probability 3‑value candidates almost daily, then play only when scored evidence clears profitability gates. Aux signals enhance (never override) what the strings say; Control Center manages state‑level and aggregate opportunities.

0) Operating model (the two “brains”)

Brain 1 — Per‑state analyst. Each state runs Stable Pattern, Digit Reduction, V‑TRAC Analyzer (Hot Zones soon). Tools output ranked candidates + evidence.

Brain 2 — Aggregate brain (Control Center). Watches special cross‑state indicators (e.g., due doubles, Blackapple, V‑TRAC repeats, “aux heat” ranks), and elevates which states deserve attention today.

Posture: We start rules‑first (config‑backed scoring + explicit gates) and log everything so later we can fit a simple supervised model; but no ML is required to ship the profitable workflow.

1) Canonical inputs & outputs (data contracts)

Daily inputs

pick3statsc4.xlsx (uploaded by user): per‑state string tables for Midday, Evening, Combined; R2/R4/R6/R8 columns 7→1.

*_draws.csv (per state): cleaned draw history (≈1,000 rows) for Aux/Blackapple/positional math; must be leading‑zero safe.

Derived outputs (by tool, per state)

Stable Pattern Extractor: tidy table of canonicalized patterns with tail/consensus/V‑TRAC mappings.

Digit Reduction (LS1/LS2): method‑by‑method sequences + terminal 3‑value sets; own↔combined deltas.

V‑TRAC Analyzer: per‑index ranking, winner bundles, HTML for humans, JSON/CSV for machines.

Aux module: overdue/recency views for pairs, doubles, sums(Blackapple), positional pressure, mirror/floaters, V‑TRAC mini‑table.

Run logging (MVP)

runs/YYYY‑MM‑DD/<run_id>/

control_center.json (aggregate watchers snapshot)

per_state/<STATE>/*.json (raw tool dicts + feature vectors)

winners/YYYY‑MM‑DD/<STATE>_<Draw>.json (labels + the feature vector used to score it)

Rationale: lets you train by doing while tools still evolve; the log layer is stable even if analysis changes.

2) Single‑Source‑of‑Truth (SSOT) for windows & thresholds

Create aux_config.py (or config/aux_features.yml) and centralize time windows + captions used across Aux, Positional, and Control Center:

Windows (proposed defaults)

Pairs: W_PAIRS = 183 (≈6 months) — good balance between stability and responsiveness.

Index/V‑TRAC recency lists & positional: W_INDEX = 360 (≈1 year) — aligns with “due/overdue” language users expect.

Doubles (combination age): effectively unbounded for top‑cap stats, but in practice use the full 1,000‑draw CSV when validating “never seen in window” claims.

Sums (Blackapple & vanilla): W_SUMS = 360 unless Blackapple variant dictates its own horizon.

Captions (self‑describing UI text)

Always print “Window: 183 draws (Pairs)”, “Window: 360 draws (Index)”, etc., in the widget headers and tooltips.

Threshold names must be semantic, e.g., PAIRS_RED_NR_GE_X, PAIRS_BLUE_NR_GE_Y (no magic numbers in code).

“Overdue” semantics

Overdue lists = by age (gap since last hit) within the active window.

Recent lists = by recency/frequency (e.g., “last 5 indexes to hit”).

Red/Blue bands are deciles/tiers on age, not frequency; recent is a separate, green‑tinted concept.

Make the V‑TRAC mini‑table read “Top‑10 Overdue (by age)” and “Last‑5 Hit” to remove ambiguity.

Why this matters: one SSOT prevents future drift where “overdue” in one table means age but elsewhere means frequency. It also makes your CT validations reproducible.

3) Scoring posture (what influences, what never overrules)

Principle: Strings lead, Aux compounds.
Auxiliary features contribute bonuses and synergy but cannot flip a low‑evidence string candidate into a play alone. This keeps you aligned with the long‑string methodology and your training examples.

Primary (from string tools)

“Is a clean 3‑value set present now?”

“Does it persist 7→1 and across R2/R4/R6/R8?”

“Own↔Combined agreement?”

“Cross‑set carryover (Set3→Set2→Set1)?”

“Straight cues (order repeats, mirror‑class stability)?”

Compound‑only (from Aux/Control Center)

Due pairs / due doubles (by age in SSOT window).

Blackapple sums status (BA‑specific sums/filters).

V‑TRAC index posture: overdue (age), recent (last‑5), or repeat‑streak.

Positional pressure & mirror echoes.

Key digit floaters (e.g., BA floaters).

Net effect: candidates get explained and boosted when Aux aligns, but not invented from Aux alone.

4) What exactly to compute (feature catalog v1)

Each feature is a boolean or scalar with a stable name so we can store it in winners logs and (later) learn weights. The list below is scoped to what you already have, plus a few low‑lift adds that string tools won’t catch on their own.

4.1 Long‑String / Digit Reduction (owned by DR module)

ls.is_3value_now, ls.first_3value_col, ls.tail_rank (1=at col‑1, 2=col‑2 …)

ls.horizontal_persist_7_to_1 (0–1), ls.vertical_rows (count of R2/R4/R6/R8 rows carrying same boxed set)

ls.cross_set_persist (Set3→Set2→Set1 true/false per column)

ls.own_combined_agree (bool) and ls.combined_faster (bool)

perm.order_repeat (straight cue), perm.mirror_class_kept (stability)

4.2 V‑TRAC Analyzer (owned by V‑TRAC module)

vtrac.index_overdue_age_rank (1–35), vtrac.is_in_last5 (bool)

vtrac.repeat_streak_len (current consecutive‑day repeats for the index)

vtrac.box8_window (≤8 perms to cover = cost favorable)

4.3 Aux & Positional (owned by Aux module)

Pairs/doubles (SSOT window): aux.pair_age_rank_AB, aux.double_age_rank_DD, aux.double_is_red_band (bool)

Sums: aux.blackapple_sum_tier (BA variant), aux.vanilla_sum_age_rank (optional)

Positional: aux.pos_top3_pressure, aux.consensus_count, aux.mirror_echo_count

Floaters: aux.floater_digit_hits (last N draws)

The adds here (repeat streak, cost window, explicit age ranks, floater counts) complement string analysis and are not already fully baked into the R2/R4/R6/R8 logic—i.e., they’re worth having as Aux features.

5) Control Center watchers (what to surface daily)

V‑TRAC Index Heatboard:
Per state: current repeat streak, last hit age, mean days‑to‑return, and whether today’s string tools point to the same index family.

Due Doubles Queue:
Top‑N double bases by age (within SSOT window).

Blackapple status:
Flag states with BA “on” (per BA variant) and cross‑show if string tools are aligned.

Aux Heat Rank (self‑contained):
A small daily table that ranks states by cumulative Aux score (no strings). Purpose: “watchlist”, not play trigger.

Results row:
Midday/Evening outcomes so watchers can be audited the next day.

These are read‑only selectors that help decide where to spend attention/budget across ~18 states.

6) Winners logging (how training starts now)

When you enter winners for a day, write:

the full feature vector from each tool,

the Aux vector + Aux score, and

the V‑TRAC bundle (index ↔ perms that actually hit).

Also export a human‑readable Markdown “AI report” that answers:

Did Control Center issue an ALERT/WATCH for this state?

Was the winner’s V‑TRAC index in the predictions?

Which Aux features matched the winner (due pair, BA sum, etc.)?

This matches your “learn while building” plan and gives you analyzable evidence now, without waiting for full ML.

7) Acceptance checks (what “done” means for Part 1)

SSOT windows live and printed in captions for Pairs/Index/Positional/Sums.

V‑TRAC mini‑table shows Top‑10 Overdue (by age) and Last‑5 Hit; both lists agree with the unified overlay used by the main V‑TRAC page.

Pairs extraction passes semantics: {AB, AC, BC} for ABC; {AA} for AAA; counts match across Midday/Evening/Combined within the chosen window.

Leading‑zero safety verified against your CT draw paste (no “070”→“70” errors).

Winners logs include the new Aux vector + score and are written under runs/YYYY‑MM‑DD/<run_id>/….

DEV‑gated System Health shows the active window counts and which CSV it read for the selected state.

8) Immediate build plan (1–2 short sprints)

Sprint A — Guardrails & truth sources

Add aux_config.py (or YAML) with SSOT windows and threshold bands, import from Aux + Control Center, and print captions in all relevant widgets.

Rename thresholds to semantic constants (e.g., PAIRS_RED_NR_GE_X); remove hard‑coded numbers from UI strings.

Factor a unified V‑TRAC overlay provider so the main table and mini‑table read the same ranked list; ensure it always returns 35 rows.

Sprint B — Feature extraction & logging

Implement aux_features.extract(state, variant) → standardized dict with the items in §4.3 (booleans/scalars).

Add aux_features.score(dict, weights.yml) → additive score + human tags (explainability).

Extend winners logging to append the Aux dict + score; update the AI report to show which Aux features scored for the winner.

Add a compact V‑TRAC repeat streak panel (Control Center) backed by a tiny JSON store built from the last N run logs.

Small, safe, and makes every future comparison trustworthy.

9) Non‑goals for Part 1 (so we stay focused)

No global “aggregate score” that blends string tools + Aux yet.

No combination‑forming heuristics or bankroll/ROI simulator changes.

No model training or hyper‑tuning; we’re only recording features & labels cleanly.

10) Do/Don’t checklist (for Codex)

Do

Keep strings → primary, aux → bonus.

Print the active windows in every widget.

Preserve explainability: always output the tags that formed a score.

Treat Combined/Midday/Evening as separate variants and compute Aux features for each.

Don’t

Don’t let Aux alone push a candidate over a play threshold.

Don’t duplicate window numbers across files—import from SSOT.

Don’t change “overdue” semantics; it’s age unless labeled otherwise.

11) Glossary (short)

3‑value set — survivors that use exactly three mirror classes.

Own/Combined — reductions on a single draw stream vs. interleaved Midday/Eve.

Tail/Consensus — last columns (3/2/1) and vertical agreement across R2/R4/R6/R8.

V‑TRAC — index‑based grouping of permutations for boxed reasoning.

Blackapple sums — BA‑style sum logic (Aux) treated as a bonus feature.

Why this is the right Part 1

It gives Codex one truth for windows/thresholds, tight semantics for “overdue,” a clear feature catalog that aligns with your methodology, and a small, safe build plan that immediately improves validation and logging—so you can start learning from real runs while you keep sharpening the string‑based analyzers.

What Part 2 will cover (next): the aggregate scoring blueprint (config‑first weights + synergy), Control‑Center ranks, the Profitability/ROI MVP wiring with simple play‑gates, and JSON schemas for the “official run” bundle so ML can plug in later with zero refactors.

3) Sums & BlackApple (keep BA as primary; add simple “sum gap” bonus)

What stays: Your BlackApple method and its derived statuses remain the main sums logic (and should keep their specialized tags).

What to add (simple & safe):

aux.sum_gap: plain recency gap for the raw digit‑sum under windows.sums.default.

# src/aux/features/score.py
def score_feature_dict(feats, weights_cfg, synergy_cfg):
    score = 0.0; contrib = {}; tripped = []
    for k, v in feats.items():
        w = weights_cfg.get(k, 0)
        if isinstance(v, bool): inc = w if v else 0
        elif isinstance(v, (int, float)): inc = w * float(v)
        else: inc = 0
        if inc: contrib[k] = inc; score += inc
    for syn in synergy_cfg:
        keys = syn["when"]; add = syn.get("add", 0)
        if all(feats.get(k) for k in keys):
            score += add; tripped.append(keys)
    return {"score": score, "contributions": contrib, "tripped_synergies": tripped}
