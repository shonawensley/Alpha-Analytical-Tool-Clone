We didn’t find any broken logic here; the implementation correctly tags “float” digits and adds weight to candidates that include them

Threshold Considerations (“Gaps”): Finally, we evaluated the various threshold values in use to see if any improvements could be made. The current thresholds (discussed above) were generally appropriate and in line with the official guidance. However, we noticed a couple of points: (1) Repeating-pair thresholds vs reality – in CT’s data, no double ever reached the Blue (71 draws) threshold, which suggests those high thresholds (71 Blue, 107 Red for doubles) are quite conservative. This isn’t necessarily a problem – doubles are rarer, so it may be by design that Red/Blue alerts for doubles are infrequent. But it’s worth noting that if the operator wants more sensitivity on overdue doubles, those values could be lowered slightly. As it stands, a double would have to be missing for a very long time (almost a third of the dataset) to trigger Blue. Since official stats likely define those cutoffs, we did not change them; just be aware that doubles will mostly show up in Purple unless a truly extreme drought occurs. (2) Midday vs Evening differences – the code uses the same draw-count thresholds for both Midday and Evening analyses as for Combined. Because Midday/Evening have half the draws (one per day each), a given draw gap represents roughly double the time span compared to Combined (which has two draws a day). The tool doesn’t currently distinguish this in the pair coloring (a pair missing 37 draws in Midday is marked Blue just as it would be in Combined). This is acceptable since the focus is on draw count rather than days, but an operator might consider slightly lower numeric thresholds for single-variant contexts if they prefer to flag similar time durations. In practice, our CT Evening/Midday pair outputs still looked reasonable with the same cutoffs – every pair had occurred within 360 draws for both, so it didn’t create any distortion. (3) No Purple for Midday/Evening in scoring – as an intentional design choice, the PDC scoring ignores Purple-level pair signals for the individual variants
GitHub
. We verified this is respected: only Red/Blue overdue pairs contribute a “RB” tag or bonus in the candidate scoring, whereas Purple (mildly overdue) pairs are not given weight for Midday/Evening to avoid overfitting minor lags
GitHub
. This is a sensible tweak that the developer explicitly implemented per request, and we confirm it’s active – none of the CT Evening/Midday suggestions were being boosted just by a Purple pair. All these threshold-related observations indicate that the logic is consistent and well-tuned. There is no “gap” in coverage – e.g. the jump from Purple to Blue thresholds is deliberate, and we did not find any pair or digit that fell through the cracks. If anything, these thresholds could be fine-tuned in the future (for example, if data or user preference suggests Purple thresholds should be 20 draws instead of 25 for faster signaling), but that would be an enhancement, not a fix. The current values are producing outputs that match the official statistics and the user’s expectations.
