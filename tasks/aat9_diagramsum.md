AAT9 System – Active Tools & Validation Components (Brain1 & Brain2)
Data Ingestion & Table Generation

Data Pipeline: AAT9 begins by ingesting the Pick3StatsC4 Excel workbook for the day and producing standardized data files. A pipeline (invoked via a script or Control Center panel) generates combined draw tables for each state under data/outputs/tables/<STATE>/. Each state’s Combined, Midday, and Evening draws are merged into CSV tables (e.g. Combined_combined.csv, etc.) for downstream analysis. In parallel, the pipeline outputs newest-first draws-only CSVs per state (e.g. data/cleaned/Florida4_draws.csv) used by auxiliary modules. This ensures that string-grid tables and raw draw sequences are up-to-date before analysis modules run. Environment helpers (like utils/path_handler.get_pick3_workbook_path() and a history selector script) allow loading specific dated workbooks for backtesting. The Control Center includes an optional “Tables Pipeline” expander to regenerate tables from the Excel source, guarding that required files exist.

Brain1 – Per-State Analysis Modules (String-Table Analysis)

Each state is processed independently by a suite of core analysis engines (Brain1 modules) that operate on the combined tables to identify winning patterns and candidates:

Stable Pattern Extractor: This module scans each state’s combined table for persistent stable digit patterns. It uses src/core/stable_pattern_extractor.py (backed by alpha_analytical/stable/* logic) to parse the table and score repeating digit sequences. The Stable extractor ingests all three variants (Combined, Midday, Evening) in one run and produces outputs in data/outputs/analysis/patterns/<STATE>/. Key artifacts include a CSV of pattern scores (e.g. <STATE>_stable_patterns_scores.csv) and an HTML report with highlighted patterns. After a run, it also generates a families CSV (<STATE>_stable_patterns_families.csv) aggregating pattern “families” (groups of related patterns). If the user enters the actual winning numbers for that date, the Stable module can perform a winner spotlight – writing spotlight CSVs (raw vs. families) that mark whether the winner’s digits or V-Trac family appeared in the top patterns. (This winner input is optional via the Stable page’s UI.) All stable pattern outputs are saved under the state’s analysis/patterns folder for that run. (Note: Legacy stable scripts and outputs have been archived; the live application uses the canonical stable extractor noted above.)

Digit Reduction Analyzer V2: The digit-reduction tool focuses on “R2 long strings” in each table (specific 9-digit strings extracted from certain cell locations) and systematically reduces them using recent draw digits. The current AAT9 implementation uses Module B – Digit Reduction Analyzer V2, a refactored pipeline that produces lean outputs for each state. The engine (src/core/module_b_digit_reduction.py) reads the state’s combined CSV and applies multiple reduction methods (A, B, C, D, E, T) to each target string, peeling away digits that appeared in recent draws. The outputs are split into two tiers:

The Reducer HTML Report (for analyst inspection) is a multi-tab HTML file showing each reduction method’s effect over the last ~7 draws. This is saved under data/outputs/analysis/digit_reduction/<STATE>/ along with a summary CSV of reduction outcomes and an optional step-by-step log (when diagnostics are enabled).

The Analyzer V2 Lean Bundle is the primary result used in aggregation. Under data/outputs/analysis/digit_reduction/<STATE>/analyzer_v2/, the system writes a minimal set of files: per_item.csv (scoring each string pattern item), top_candidates.csv (the highest-ranked predicted combos), and a meta.json with run metadata. An HTML file with stacked charts may also be produced per variant for QA. These lean outputs capture the essential evidence (pattern clusters, scores, etc.) without any embedded winner data. By design, Digit Reduction V2 does not automatically overlay winners in its output; any winner-hit flags are added later by a central process (see Winners Logging below). Training bundles can be created to archive these outputs (and optional step logs) under a timestamped training_sets/ subdirectory for offline learning, but they exclude winners unless explicitly enabled. (Older verbose JSON logs and redundant outputs have been retired in favor of this lean output set.)

V-TRAC Pattern Analyzer: The V-TRAC module evaluates each state’s data table through the lens of V-Tracs (a transformation grouping digits by 5s). AAT9’s V-TRAC Analyzer is fully integrated and considered a “cornerstone” module. It processes the combined CSV (and optionally Midday/Evening variants) to rank all 35 V-Trac indices by the strength of their repeating patterns. The main logic resides in the Streamlit app’s “V-TRAC Analyzer” tab and its helpers: scripts/streamlit_app_with_analyzer.py (UI and control flow), utils/vtrac_utils.py (pattern matching & scoring functions, including the BOXED_VTRAC_REFERENCE table), and utils/bundler.py (which merges predictions with logged winners). For each run, V-TRAC produces human-readable reports and machine-readable predictions:

HTML Analysis Report: An interactive color-coded report highlighting where top V-Trac patterns appear in the table. This is saved under data/outputs/analysis/vtrac/<STATE>/... (or made available via the UI). If the user logs the day’s winning numbers in the “Log & Highlight Winners” panel, the report will visually mark those occurrences as well.

Prediction JSON: A JSON file capturing the ranked V-Trac predictions for the next draw (top indices, scores, etc.), saved to data/outputs/predictions/. This is a raw output of the V-Trac analysis for programmatic use.

Winners JSON: If winners are entered, the app saves the actual winning numbers (Midday/Evening) to data/outputs/winners_json/.

Bundle JSON: A combined learning payload that merges the predictions and the actual outcome, written to data/outputs/bundles/ as {state}_{date}_bundle.json. This “bundle” is crucial for model training – encapsulating what was predicted vs what won.

Winners Highlight CSV/HTML: When winners are logged, the app can generate a winners-highlight version of the table (showing where the winning combo appears in each V-Trac index) and save it under data/outputs/analysis/winners/<STATE>/. This provides a quick visual verification of whether the predicted patterns caught the winner.
In summary, the V-TRAC Analyzer is actively wired into the app via the Streamlit UI and produces both rich visual outputs for analysts and structured JSON for the aggregator/ML brain. It also provides the interface for daily winner logging, which is central to AAT9’s validation loop.

(Note: The Stable, Digit Reduction, and V-Trac modules are all actively used in the current system. Experimental ideas like “Hot Zones” are not yet implemented, per the roadmap, and older tools have been archived to avoid confusion. The focus is on these three core analyzers, each of which produces analysis outputs and (optionally) training artifacts.)

Auxiliary Feature Integration (Aux Tools Layer)

In parallel with the core string-table modules, AAT9 integrates several auxiliary analytics that operate on the draw history to provide context and confirmatory signals. These Aux tools do not analyze the combined string grids; instead they use the draws-only data (*_draws.csv) to surface patterns like due numbers, pair frequencies, and special alerts. Key auxiliary components include:

Blackapple (BA) Analyzer: Blackapple is an auxiliary scoring engine that compiles multiple draw-based signals into a ranked list of candidate combos for each state. It looks at factors such as mirror pairs, “digital root” due sums, extreme or mixed pattern gaps, “floating” overdue digits, and remaining pair patterns to assign a small score (0–5) to potential next draws. Blackapple runs on each state’s recent draws (typically last 100+ draws, per CSV) and yields up to 12 top candidates with tags indicating which triggers they hit. Rather than writing files, BA surfaces its output in the Control Center’s UI: each state/variant gets a BA score, status (OFF/WATCH/ALERT), trigger summary, and example combos displayed in a centralized table. Under the hood, the BA logic lives in modules/blackapple.py. To avoid import conflicts with other “modules” packages, the app loads it via an absolute import helper (_load_blackapple_real() in src/app.py), ensuring the Blackapple analyzer is pulled from the project’s own modules folder. Blackapple obtains its input through the shared Aux loader (see below), which provides the state’s newest-first draw list for the chosen variant. This module is fully active – the Control Center uses Blackapple’s output to flag states with overlapping signals and potential play candidates. (At present, BA output is shown in-app only; a future update will allow logging these alerts or exporting daily summaries.)

Due Doubles Tracker: The Control Center also highlights states that are “due” for doubles (a Pick-3 number where two digits are the same, like 112). A doubles tracking routine scans each state’s draw history to find how long it’s been since a double hit. The Control Center presents a cross-state table listing each state and variant, the number of draws since its last double, and possibly the last seen double (with the data source path for verification in dev mode). This uses the draws CSVs (load_state_draws) to count back until a double is found. The tracker logic is embedded in the Control Center page (no separate file output), and it updates for Combined, Midday, and Evening independently. In effect, it surfaces “hard due” states that haven’t seen any double in a long stretch – a simple but useful aggregate indicator.

Positional “Heat” Tracker: Another aux feature is the positional pressure analysis. This looks at each digit position (1st, 2nd, 3rd) within the draws to find the top 3 most overdue digits for that position in each variant. The results are shown as a compact grid or badge. In the Control Center UI, each state row includes a P1/P2/P3 heat badge – e.g. highlighting if a particular position has a digit that’s extremely overdue (marked in red if beyond a threshold). This positional tracker is powered by modules/module_d_auxiliary_tools/refactored/positional_tool.py (part of the refactored aux tools) and uses the draws CSV as input. It doesn’t produce external files; instead, the System Health/Dev captions in the UI can show the underlying data (e.g. resolved CSV path and counts) for verification. The Positional Tracker integration was recently restored and hardened – ensuring the loader registers the aux modules correctly and that variant-specific CSVs (Midday/Evening) are handled if present. This aux component is actively used to give quick visual cues in the Control Center about positional digit gaps.

Pairs and V-Trac References: The Aux page (and underlying logic) also includes a repeating pairs analysis and a V-Trac reference for additional context. The codebase contains modules/analyze_pairs.py and modules/vtrac_reference.py which are staged to provide these auxiliary calculations. For example, the Aux page displays repeating or non-repeating pairs tables (with color coding to indicate severity) – these help identify if certain digit pairs are appearing frequently or have not appeared (“purple pending” highlights for long-out pairs on Combined variant). The vtrac_reference module exposes a lookup for V-Trac values (e.g. mapping digits to V-Trac indices) which Aux tools can use to label outputs (ensuring consistency with the core V-Trac analyzer). These aux computations run in-memory and render directly in the Auxiliary Tools page as tables or captions; they do not write outputs to disk. They provide supporting evidence (like highlighting a severe pair gap or showing V-Trac label definitions) to complement the main modules.

All auxiliary features are integrated into the app’s workflow to augment decision-making but kept isolated from the core data to avoid side effects. The modules/aux_loaders.py plays a key role here – it provides a unified function load_state_draws(state, variant) that fetches the appropriate CSV (Combined by default, or Midday/Evening) and returns the draws list. The Control Center and Aux pages rely on this loader to get data for BA, doubles, positional, etc., with a consistent contract (newest-first strings). The app uses helper calls _load_aux_loaders_real() to import this loader module at runtime. Thanks to these integrations, Brain1’s pattern findings can be cross-checked against Aux signals – for example, a state with strong stable/V-Trac patterns and a high BA score with hard-due positional might be flagged as especially promising.

(Aux features that are planned but not yet active – like “Hot Zones” or advanced compound scoring – are not part of the current live system and are omitted here. The above Aux modules represent the working set wired into AAT9 now.)

Brain2 – Aggregate Control Center & Validation Flows

Brain2 (Control Center) is the aggregation layer that pulls together all per-state insights and oversees cross-state comparisons. In the Control Center interface, each state’s status is summarized using both the core module outputs and auxiliary alerts to guide decision-making:

Cross-State Dashboard: The Control Center’s main page shows a multi-column table per state (and variant) including fields like Due Double count, Blackapple Score/Status, and possibly composite rankings. For example, a row might read: Florida (Combined) – BA Score 3 (ALERT), Triggers: Mirror+Root, #Candidates 12, Examples: 507, 160, 934, Positional Heat: P2🔥, Double Out: 25 draws (no double in last 25 draws). This consolidates the key outputs:

Due Doubles: The number of draws since a double hit, often with a dev-only caption of the last double and source CSV.

Blackapple: The BA composite score (0-5) with a status label (OFF/WATCH/ALERT) and the trigger factors that fired. Only the top 3 example combos are shown inline for brevity, with the full list of 12 candidates available under an expander for each state.

Positional Badge: A compact indicator if any position is “hard-due” (e.g. a red number if a position’s top overdue digit exceeds the threshold). This gives a quick glance at positional pressure in that state.

(Planned integration) Overall Rank: The vision is to combine module outputs (Stable, Digit, V-Trac scores) and aux scores into a single aggregate ranking or score per state. This would denote which states are most favorable for play on a given day. In the current implementation, this compound “Aggregator score” is still in development – for now, the operator uses the presented data (pattern scores from module pages and the Control Center’s BA/Doubles info) to make judgments. Hooks for combined scoring are being laid (e.g. capturing module outputs in JSON, computing “analysis ranks” externally), but a final computed rank is not yet automatically displayed in the UI.

Winners Logging & Validation: A crucial function of Brain2 is to validate and log the performance of Brain1 predictions against actual outcomes. Rather than each tool writing its own winner-hit metrics, AAT9 has centralized this in a Winners Module (a unified validation pipeline). In practice, after each draw’s results are known, the system (or user) logs the winning numbers for that date, and a batch process consolidates all tool outputs to create a “winner map”. This Central Winners Module (script often called build_winners_log.py) reads the lean artifacts from each tool and produces a holistic record of which patterns hit the winner. According to the design spec, it classifies each winner in terms of exact match, boxed match, V-Trac family hit, and V-Trac straight alignment (the four hit levels), using inputs from: Stable’s scores/spotlights, V-Trac’s compact report and highlight data, Digit Reduction’s top candidates, and Aux signals. This yields a per-date winner_map.json and a CSV of flags (winner_flags.csv) stored under data/outputs/winners/<YYYYMMDD>_*. Each JSON entry contains the state, variant, winning number, and a breakdown of which modules caught it (e.g. Stable’s best rank for that number, which V-Trac index it fell into, Digit Reduction rank if any). These outputs serve as the “ground truth” for scoring the tools and will feed any future ML models with labeled outcomes. Notably, the Control Center (Aggregator) is responsible for orchestrating this winners log creation – it is the only component that writes these machine-readable winner artifacts in the live system. By design, all individual modules refrain from generating final winner-score files (to avoid duplication and inconsistencies); instead, the aggregator uses the common outputs and a unified method to produce the official winner logs. (For instance, Digit Reduction V2’s code will only overlay winners if a diagnostic mode is on – in normal runs it defers to the central process for marking hits.)

Sharepacks & Analysis Bundles: To facilitate deeper reviews and offline analysis, AAT9 employs “sharepacks” – structured folders bundling all relevant outputs for a given date. After a daily run (or batch backtest), the system can collect each state’s results into sharepacks/YYYY-MM-DD/<State>/... directories. A Stable sharepack for a state contains that day’s stable pattern CSVs, any winner spotlight CSV, and even the Stable config/metrics JSON. Similar bundles exist for V-Trac and Digit Reduction (and potentially Aux) so that an external reviewer or another system can easily consume the analysis without running the app. There are utility scripts like TOOLS/run_vtrac_share_bundle.py which generate a summary markdown (summary.md/csv) of V-Trac results across states and a vtrac_compact_report.json/csv – a condensed scoring of V-Trac predictions with weights applied. The compact report is essentially the aggregator-consumable form of V-Trac outcomes (including any state-specific priors or config tweaks) and is treated as a contract output for the aggregator. In fact, the aggregator (Brain2) explicitly consumes the vtrac_compact_report.csv/json and the summary files as inputs to its decision logic. The Checkpoint log confirms that as of V-Trac v1 finalization, “Aggregator consumes vtrac_compact_report.{csv,json} + summary.{md,csv}; winners HTML lives in outputs for reference. Lane-aware ranking will be handled centrally.”. This means the aggregator trusts those compact metrics for each state’s V-Trac strength, and will later combine them with Stable and Digit Reduction signals. The sharepack ZIP (often named vtrac_validation_full_payload.zip for a batch run) can be created to include all state JSONs, reports, and summary in one archive for sharing. Similarly, for Stable patterns, a special “Packet-2” run can regenerate stable outputs with winners and collect Control Center aggregates (BA, doubles) for that date – effectively a sharepack that allows analysis away from the live app. These sharepacks are used during final validation and documentation to ensure that the data flow is transparent and reproducible outside the Streamlit UI.

In summary, the actively wired components of AAT9 consist of the core per-state analysis modules (Stable Pattern Extractor, Digit Reduction Analyzer V2, V-Trac Analyzer) that generate scores and candidate predictions for each state, and the aggregate Control Center layer which integrates auxiliary features (Blackapple alerts, doubles/positional trackers) and oversees cross-state validation and logging. Every module has clearly defined input sources and output artifacts: Stable and V-Trac read the combined tables; Aux tools read the cleaned draws; each writes results to a dedicated folder under data/outputs/analysis/... (patterns, digit_reduction, vtrac, etc.). Critical “lean” outputs like the Digit Reduction per_item.csv & top_candidates.csv and the V-Trac compact_report.csv are consumed by the aggregator for final decision-making. Meanwhile, validation scripts (such as tools/vtrac_validate.py and batch variants) and the Winners Module ensure that all predictions are systematically checked against actual outcomes, producing unified logs and JSON evidence for each draw. The design avoids deprecated or duplicate pathways – for example, legacy table formats and old runner scripts have been archived, and winner overlays are generated only in one place (Control Center) to serve as the single source of truth.

This cohesive architecture (Brain1 + Brain2) means that each state’s data flows through the same pipeline of table generation → module analyses → lean outputs, then up into the aggregator for cross-state comparison and final validation. The canonical file paths (e.g. data/outputs/analysis/<module>/<STATE>/... for analysis results, data/outputs/winners/<DATE>/... for winner logs, and sharepacks/ for packaged runs) can be considered authoritative wiring points in the system. These are the active components and data flows that will form the foundation of the Part 1 architecture diagram, illustrating how the AAT9 application processes lottery data into insights and how each tool connects to the overall validation and decision loop.
