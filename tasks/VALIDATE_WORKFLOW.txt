Q2) Shared schema — what it really means (and how it relates to JSON tables)

The “shared schema” is not a list of features all trackers share. It’s the standard output row shape that every alert writes so Control Center can display it consistently.

The schema fields are explicitly listed as:
state, date, alert_id, variant, set, draw_idx, col, k_canon, strength, action, cap_lines, decay_draws, badges, evidence_json

Anything “feature-like” that is alert-specific goes into evidence_json. That’s why the schema includes that field explicitly.

So: if you’re worried “we can’t currently identify certain features,” the first pass doesn’t require stuffing them into JSON tables. You can:

compute them in the tools (Stable/DR/VTRAC/Hot Zones) and

attach them as evidence in evidence_json.

Q3) Mix of table-specific features vs analytical tool features?

Yes — the rollout checklist is explicit that you cannot depend only on string tables; you need computed columns/flags from the analytical tools too.

Example: the checklist calls out needed Stable computed columns (cons_*, rowcov_*, perm_*, order dominance, etc.) and also flags from other modules like Digit Reduction / VTRAC / Hot Zones.
And the “module-level field additions” list is very explicit about extra fields to add to Stable (consensus tail, row coverage, perm collapse, order dominance), Digit Reduction (survivor/doubles bias), VTRAC (repeat risk), and Hot Zones (star levels).

Q4) “If these features aren’t in the tools, is it doable to add them?”

Yes — the spec expects exactly that.

You’re not “misunderstanding”: the build plan literally includes “module-level field additions” and a rollout checklist that requires adding computed columns and small flags so alerts can be detected deterministically.

So if you don’t find a field in the tool output, that’s not a dead end — it’s a known integration step.
