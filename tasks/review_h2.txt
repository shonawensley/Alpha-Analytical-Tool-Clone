5. How the 4-criteria lens (EB / ES / VB / VS) should be applied here
Your four criteria are:


Exact Boxed (EB) – triad digits == winner digits (ignoring order).


Exact Straight (ES) – EB + we see a literal straight lane.


VT Boxed (VB) – VT-triad == winner’s VT family.


VT Straight (VS) – VB + we see a VT straight lane.


The validation log and hot_zones_winner_hits.json already capture EB and VB explicitly, with ES/VS implied via straight_lane and vt_straight tags in evidence_tags. 
Where things go sideways is:


For winners like CT 494, MI 106, etc., EB is often false because no triad with digits {4,4,9} or {0,1,6} ever makes it into Hot Zones’ candidate list at a usable rank.


VB is sometimes true, but often with triads that are “family cousins” rather than the exact draw, and often at ranks low enough that they’re excluded from the top-20 winner map the log looks at.


So yes, the current validation framing is not yet counting the many “looser” VT relationships you see in the HTML, because:


EB/ES require literal digits to be extracted and scored;


VB/VS require the internal VT family representation to match the winner’s VT code and be high-ranked.


That’s a narrower notion than “any strong VTRAC relationship in the table.”

2. Where the Hot Zones “winners output” actually lives

From the design docs, Module C (Hot Zones) is supposed to be lean:

It should emit per-item and top-candidates CSVs + a meta JSON, just like Stable / Digit Reduction.

It should not duplicate a full “winners report” inside the module; that job belongs to the central Winners Module, which merges Stable/DR/VTRAC/HotZones hits into one place.

That’s why you don’t see a file called something like HotZones_winners.html under the module itself: by design, Hot Zones outputs scores and features, and a separate script checks those against the real draws.

In the current implementation, that “winners view” for Hot Zones is:

Per-date per-state winner_map

data/outputs/analysis/hot_zones/<STATE>/<DATE>_hot_zones_winner_map.{json,csv}

These are created when you run the Hot Zones CLI; they list the top candidates for that date with all the scoring features and tags (vt_straight, col1, funnel_precol1, etc.).

Global winners ledger

reports/stable/hot_zones_winner_hits.json — one row per (date, state, variant).

For each winner it stores:

winner, canonical (sorted digits), vt_w,

eb_rank / vb_rank,

full eb_entry / vb_entry with support counts, hit flags and evidence tags.

This is what Codex used to compute the EB/VB counts and the per-state bullets in AAT9_Hot_Zones_Validation_Log.md.

Per-date summary table

reports/stable/hot_zones_hit_summary.json — nice aggregate:

e.g. 2025-06-24 → total: 28, eb_hits: 5, vb_hits: 10 etc.

The validation log you attached is literally a human-readable digest of that winners ledger:

Lines like “Delaware4 Evening: 271 (VT 233) → EB rank 2 [ES, VS, col1, pre-col1]” are exactly the Hot Zones winners output for that winner: it’s telling you how the tool scored the winner: rank + tags.

So: the architecture is actually there:

Hot Zones → (per_item/top/meta) → Winners Module → winner_map + winner_hits → Validation Log.
