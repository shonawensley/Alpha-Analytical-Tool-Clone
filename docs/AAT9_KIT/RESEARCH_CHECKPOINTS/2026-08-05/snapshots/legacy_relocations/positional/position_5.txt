Great question — and you’re thinking about it exactly the right way: everything is “from now, backwards.” The only knob we’re turning is how far back we look (the window). Here’s how to read “360 vs 150,” why they’re different on purpose, and what “SSOT” means in this context.

TL;DR (the short, practical answer)

All analyzers scan the latest N draws, newest → older. No averages, no future leakage.

Pairs should use a deeper window (≈360) so the repeating‑pair thresholds (RED ≥ 107, BLUE ≥ 71) are actually reachable. Keeping it at 100 makes true “reds” mathematically impossible to see.

Positional tracker works best with a mid window (≈150) by default: it stays “about now,” but smooths a little noise so the Top‑3 per position are stable and useful. (You can still slide to 120/180 as you prefer.) The positional engine is draws‑only and orthogonal to Pairs/V‑TRAC/Sums — that’s why it composes so well.

SSOT = Single Source Of Truth. We centralize each window/threshold in one place and make every feature read from that constant so behavior is predictable and easy to audit. For Pairs, this is the PAIRS_ANALYSIS_WINDOW set to ~360 (instead of scattered draws[:100] slices).

Why two different windows?
1) Pairs: deep window (≈360)

What we’re measuring: longest‑out age of unordered digit pairs (e.g., 11, 16, 69), especially repeating pairs (doubles).

Why 360: Your RED/BLUE repeating thresholds (RED ≥ 107, BLUE ≥ 71) require a window comfortably above 107. At 100, you cannot observe a red 107+ even if it’s truly overdue — the signal is clipped. Setting a constant window (≈350–360) fixes that and keeps Pairs aligned with how other overdue checks already scan deeper history.

2) Positional tracker: mid window (≈150)

What we’re measuring: per‑position “draws‑since” (P1/P2/P3) and cross‑variant agreement (XVAR consensus), i.e., where pressure sits right now.

Why 150: Positions need to be current and responsive; a 150‑draw slice is a practical “recent history” that’s long enough to stabilize ranks but short enough to reflect regime changes. The positional analyzer is explicitly designed to be draws‑only and orthogonal to Pairs/V‑TRAC/Sums, which is why it pairs so well with those other features without double‑counting.

Mental model: With any analyzer we always scan the latest N draws. If a digit last appeared 22 draws ago, DS=22 no matter whether N=150 or N=360. The difference is who shows up in Top‑3 and how stable those ranks are: a larger N stabilizes but can “flatten” recency; a smaller N is twitchier.

“But I want it as‑of‑today”

You have it. Every window is anchored at the most recent draw and goes backwards. The windows are about scope (how long a memory we allow), not a different interpretation of “current.”

Pairs: needs a long memory to honor the 71/107 thresholds you use operationally.

Positions: benefits from a medium memory so pressure is actionable for today’s play.

Recommended “standard” settings (so you don’t have to tinker)

Pairs (Repeating & Non‑Repeating): PAIRS_ANALYSIS_WINDOW = 360 (SSOT constant). Caption it in the UI.

Positional tracker (P1/P2/P3): default 150 with a slider (120–180 typical). Keep hard‑due styling at the current thresholds (C=55, M/E=40).

Combos / V‑TRAC overlays: keep using the deeper caches (often 1000) you already rely on for combo DS and index overlays; those were never the problem — the 100‑draw cap was only in Pairs.

This gives you a universal baseline you can ship and forget. Any future tuning can be learned/auto‑suggested, but you don’t need to hand‑tune day to day.

What exactly is SSOT here?

SSOT (Single Source Of Truth) means we put each critical knob (like the Pairs window) in one exported constant and make every caller use it. No stray [:100] slices hiding in the UI layer; one value, used everywhere, and documented in the preflight. In our guardrails we called this out explicitly for Pairs as “Pairs depth as a single source of truth,” and we proposed exporting PAIRS_ANALYSIS_WINDOW and aligning captions/tests to it.

The same pattern applies to:

Thresholds: one helper that names/owns RED/BLUE/PENDING expectations — prevent label swaps and keep captions honest.

Variant draw sourcing: one loader path (cache → canonical fallback) so every analyzer sees the same data shape.

For Blackapple (BA) this idea already exists conceptually: BA reads one canonical draws feed and emits one small artifact that other pages read — no duplicate logic, no shadow copies. SSOT keeps Aux consistent and debuggable.
