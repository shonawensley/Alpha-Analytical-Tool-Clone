# AAT9 Analysis Arena - RUNS_2 Artifact Review Map

Purpose: give a human reviewer one clean map of the artifact families that
exist for an Analysis Arena window, where they live, how they relate to the
cadence, and what is still fragmented.

This is a review/navigation artifact. It does not change runtime behavior.

## Bottom Line

The current Analysis Arena branch is easiest to understand as a five-layer
review system:

1. predictive Brain 1 SSOT
2. predictive Brain 2 SSOT
3. post-results validation SSOT
4. control-arm comparison SSOT
5. window-close learning SSOT

The post-results and window-close layers are already strong and uniform.

The predictive side is also strong analytically, but less human-friendly,
because it is split across:

- runtime receipts in `RUNS_2/WINDOW_<...>/ANALYSIS_ARENA/`
- state-local sharepack analysis in `sharepacks/_predictive/<D>/<STATE>/analysis/`
- optional standalone predictive report tooling that is not clearly auto-emitted
  by the main pre wrapper

So the problem is not missing Arena-era truth. The problem is packaging and
navigation.

## Canonical Five-Layer Model

### 1. Predictive Brain 1 SSOT

- canonical per-state pre-draw Arena evidence
- lives in `sharepacks/_predictive/<D>/<STATE>/analysis/`
- tells you what the state-local tools and aggregated Arena logic produced

### 2. Predictive Brain 2 SSOT

- canonical cross-state board/runtime layer before results
- lives in `RUNS_2/WINDOW_<...>/ANALYSIS_ARENA/`
- tells you how the day looked across all tracked states

### 3. Post-Results Validation SSOT

- canonical reverse-engineering layer after results
- lives in `RUNS_2/WINDOW_<...>/VALIDATION/`
- includes per-state Master Validation, Brain 2 Master Validation, Control
  Center, and Day Synthesis

### 4. Control-Arm Comparison SSOT

- canonical old downstream realized-output baseline
- lives in `RUNS/`
- includes Candidate Universe grades and Play Card grades
- remains comparison-only, not Arena truth

### 5. Window-Close Learning SSOT

- canonical cross-day learning and opportunity-gap layer
- lives at the window root itself
- includes performance gap, pure finalist scorecard, translator learning, deep
  hit analysis, C1/C2 frontier, and related research surfaces

## Dual-Performance Model

There are effectively two performance surfaces being tracked:

1. the old downstream realized-output control arm
2. the newer Arena-native diagnostic/performance arm

The first tells you what the old combination-forming / Play Card system actually
realized.

The second tells you what the Arena preserved, what the downstream arm failed
to convert, and where future translator / combination-forming / budget rebuild
work should focus.

Review rule:

- compare these two arms
- do not blend them
- do not treat control-arm realization as the definition of Arena truth

## Recommended Human Review Order

When reviewing one completed window such as:

- `docs/AAT9_KIT/FINAL VALIDATION/RUNS_2/WINDOW_2026-03-09_to_2026-03-23/`

use this order:

1. predictive Brain 2 / board layer
2. post-results validation layer
3. predictive Brain 1 state evidence layer
4. control-arm comparison layer
5. window-close learning layer

That ordering keeps:

- board posture first
- reverse-engineering and truth second
- raw state-local predictive evidence third
- downstream comparison fourth
- cross-day learning and opportunity-gap synthesis last

## Artifact Families

Primary location:

- `<D>__BOARD_REVIEW_BUNDLE__analysis_arena_day_review.{md,json}`

- `<D>__TRANSLATION_SANDBOX_SEED__analysis_arena_day_review.{md,json}`

- `docs/AAT9_KIT/FINAL VALIDATION/RUNS_2/WINDOW_2026-03-09_to_2026-03-23/ANALYSIS_ARENA/2026-03-09__BOARD_SCOREBOARD__analysis_arena_day_review.md`

Cadence status:

- generated by `run_analysis_arena_cycle.py pre` / `pre-range`

### 2. Per-state predictive Brain 1 evidence

Purpose:

- preserve what the state-local tools are actually producing before the draw
- give the clearest “what did the system know before results?” surface

Primary location:

- `sharepacks/_predictive/<D>/<STATE>/analysis/`

Core files:

- `aggregated_analysis_arena__tool_only__arena_v0.{md,json}`
- `translation_sandbox_seed__tool_only__arena_v0.{md,json}`

- `signals_bundle__tool_only__arena_v0.json`

- `digit_reduction/<STATE>/*`
- `vtrac/<STATE>/*`

Example:

- `sharepacks/_predictive/2026-03-09/OntarioCanada4/analysis/aggregated_analysis_arena__tool_only__arena_v0.md`

Cadence status:

- generated by the current pre wrapper
- this is the real Brain 1 per-state predictive surface

### 3. Standalone predictive report shell

Purpose:

- human-readable per-state pre-results review shell
- explicit Markdown companion to the predictive sharepack

Location when generated:

- `docs/AAT9_KIT/FINAL VALIDATION/RUNS_2/PREDICTIVE/<D>__<STATE>__PREDICTIVE__tool_only__arena_v0.md`

Generator:

- `scripts/tools/create_predictive_run_report.py`

Current posture:

- the standalone tool exists
- the top-level predictive portfolio reports exist
- the current main `pre` / `pre-range` wrapper does not clearly auto-emit these
  per-state predictive Markdown reports in the same uniform way the post
  validation layer is emitted

This is the main predictive-side integration gap.

### 4. Predictive portfolio triage

Purpose:

- fast cross-state predictive triage before results
- quick “where should I look first?” surface

Location:

- `docs/AAT9_KIT/FINAL VALIDATION/RUNS_2/PREDICTIVE/`

Files:

- `<D>__PREDICTIVE_PORTFOLIO__tool_only__arena_v0.md`

Cadence status:

- present and useful
- cross-state only
- not a substitute for per-state predictive review

### 5. Per-state post-results Master Validation

Purpose:

- reverse engineer wins and misses per state after results exist
- tie winners truth to predictive evidence, translation surfaces, and control arm

Location in window runs:

- `docs/AAT9_KIT/FINAL VALIDATION/RUNS_2/WINDOW_<...>/VALIDATION/`

Naming:

- `<D>__<STATE>.md`

Important note:

- these are the “Master Validation template completed” files
- they do not contain `MASTER_VALIDATION` in the filename
- this is why they are easy to think are missing

Example:

- `docs/AAT9_KIT/FINAL VALIDATION/RUNS_2/WINDOW_2026-03-09_to_2026-03-23/VALIDATION/2026-03-09__OntarioCanada4.md`

Cadence status:

## What Is Strong vs What Is Weak

Strongly integrated today:

- board runtime receipts
- per-state Master Validation
- Brain 2 Master Validation
- Control Center daily report
- Day Synthesis
- doubles inventory
- window-close learning stack

Weaker / fragmented today:

- per-state predictive Markdown shell emission
- discoverability of state Master Validation naming
- unified one-page map of where all review artifacts live

## Practical Review Package For One Window

If the goal is to review one strong window deeply, assemble it as:

1. `ANALYSIS_ARENA/` per-day board receipts
2. `VALIDATION/` per-day:
   - state reports
   - Brain 2 Master Validation
   - Control Center
   - Day Synthesis
   - doubles inventory
3. `sharepacks/_predictive/<D>/<STATE>/analysis/` for any state you want to
   inspect deeply
4. `RUNS/` control-arm grades for the same dates
5. window-root closeout artifacts

That is the cleanest current human-review package.

## Recommended Next Cleanup

If you want the review experience to become truly clean, the highest-value
follow-up changes would be:

1. keep this artifact map current and linked from the main portal
2. decide whether `create_predictive_run_report.py` should be called from the
   main `pre` / `pre-range` wrapper
3. optionally add a per-window manifest that lists:
   - predictive artifacts
   - board receipts
   - validation artifacts
   - control-arm grades
   - window-close artifacts

That would remove the main remaining ambiguity.
