3. Implementing the 12 indicators: how to think about them

You said it very clearly: every indicator is really “a profitable event that prints money” – an identifiable situation that historically leads to good outcomes. The docs echo that: the 12 profitability indicators sit on top of the existing tool outputs and winners logging as an alerts layer, not a new engine.

So here’s how I’d guide Codex.

3.1. Treat each indicator as a pure detector, not a full profit system

Unverified but strongly recommended:

For each Axx:

Inputs

What does it need? (eg. string‑table environment pattern, BA status, due‑double rank, vt_repeat, positional/aux tags).

List those explicitly from your 12‑PART docs.

Condition

One clear boolean: “does this indicator fire for state S, variant V, date D?”

Inside: check the pattern in tables/JSON; optionally AND/OR aux features.

Alert row emission

If true → emit one row into the alert table with:

alert_id="A03" (or whatever)

trigger_reason = short text like “due double rank≤N with BA support and vt_repeat”

any relevant numeric fields (ranks, counts, vt_index, etc.)

Hit tagging

Use the same downstream logic you already have (winner vs alerts) to tag “hit/miss” & hit class. Don’t make the indicator’s code worry about winners; keep that shared.

All the profit & ROI stuff can come later, off the alert+hit table. Right now we just want each “thing we care about” to be detected reliably and logged.

3.2. Which data to read: CSV tables vs JSON vs Hot Zones vs aux

From the wiring doc:

Stable/DR/V‑TRAC use combined CSV tables under data/outputs/tables/<STATE>/... as their core input.

Hot Zones already consumes the JSON mirror data/outputs/json_tables/<STATE>_tables.json per state.

Given that:

For table‑shape / environment‑shape indicators (things like ladders, hot strings, method‑T vs LS1/2 type logic), I’d have Codex use the JSON table mirror as the primary feed.

It’s one file per state/day, already structured by section/set/draw/column – exactly what your indicators describe.

It avoids re‑opening multiple CSVs and keeps the logic close to what Hot Zones does.

For aux‑driven conditions (positional, sum, consensus, BA‑flavoured features), treat Aux as a separate snapshot:

Run aux once per state/variant (which you already do in Brain1).

Persist a small JSON or CSV summary per state/day/variant that Control Center can read – not the full UI tables. (Unverified, proposal.)

The indicators then just look up the aux snapshot and combine it with JSON‑table facts.

For BA/doubles/v‑trac‑repeat: keep using the draws + BA reference code that already powers the BA summary & doubles table.

So answer to your specific doubt: yes, using the JSON table mirrors as the main lens for the trackers is a good idea, as long as the fields you care about (set, column, draw, row type) are present – which they are for Hot Zones already.

3.3. Don’t overcomplicate aux integration

From the Auxiliary Integration doc, aux features are designed to be:

Config‑driven (weights & feature flags live in config, not hard‑coded).

Transparent (each aux contribution is logged alongside the winner so you can see what helped).

Non‑overriding (they never create winners, they just compound with strings).

So for A01–A12:

Decide for each indicator whether aux is required or just nice‑to‑have. Example:

“Axx: pure string‑table pattern” → aux optional; you might just log available aux support as context.

“Ayy: profitable when BA + due double + vt_repeat align” → aux/BA required.

In code, reflect that as:

If necessary aux data is missing for that state/variant/date, do not fire the indicator; instead log a small “skipped due to missing aux” entry in a debug channel. (Unverified, but helps keep stats honest.)

This keeps indicators logical and prevents you from quietly firing half‑defined signals.
